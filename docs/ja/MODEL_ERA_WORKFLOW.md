# 新しいモデル環境での使い方 — 0.8.0

## 利用者のモデル選択を維持

GPT-6 Astra と GPT-6.1 Sol は、ホストが実際に公開するツールから同じ範囲制限付きソース根拠を利用できます。利用者が選んだモデルと推論強度を維持します。プラグインはモデルを選択せず、特定モデル・リモートAPI・有料アカウントを要求しません。取得契約の改善を測定済みのモデル優位性と見なさず、モデルA/B結果も主張しません。

## AI: ローカル MCP と固定した根拠

Windows・macOS・Linux と既存の Python 3.9+ を使用します。公式 Skills-only パッケージは分析器・オフライン HTML・ローカル MCP 設定手順を含みます。ローカル stdio サーバーには同一バージョンの完全パッケージを使い、公開エンドポイントは不要です。依頼された設定だけを変更し、他の設定を保持して、新しいホストプロセスで実際のツール公開を確認します。ファイルの導入だけでは直ちに呼び出せません。

まず登録ワークスペースとソースの鮮度を確認します。完全パッケージには既存のワークスペース・状態・検索・近傍・履歴・差分・来歴の7個と `ontology_large_modules`、`ontology_large_search`、`ontology_large_neighbors`、`ontology_evidence_bundle` の計11個の読み取り専用ツールがあります。通常の関連照会は同一スナップショットに固定し、具体的な質問には根拠バンドルを使います。大規模プロジェクトではモジュールを一覧し、カタログを固定し、正確なモジュールルートを検索して、選択した単一モジュール内の経路を調べます。モジュール間の呼び出し解決は行いません。

初期化・更新は別途許可された CLI 書き込みです。MCP は任意パスではなく登録IDを受け、インストール・更新・対象コード実行・ソース送信を行いません。ページ数や探索上限は結果の限界として示します。

## 人: オフライン HTML を探索

`graph.html` をローカルで開きます。モジュール概要からシンボルを検索・選択し、ソース位置と関係根拠を確認します。構造・影響・変更は異なる問いを扱います。検索とページ付きテキストで、折り畳まれた項目や画面外の項目にもアクセスできます。表示数は画面の範囲でありコード全体ではありません。

表示レイヤーと1・2・3段階の呼び出し強調は独立です。レイヤーを一つずつ追加し、4段階以上は確認して拡張します。カメラのフォーカス・ズーム・Shiftドラッグ移動を別々に使います。キーボード、動きを減らす設定、テキスト一覧も利用できます。集約とカメラ移動はソースや実行の新しい根拠ではありません。

## 根拠・プライバシー・確認

ソース関係 `observed`、提案 `inferred`、`runtime_unknown` を区別します。パス・行と規則根拠を示し、鮮度、パーサーの範囲、未解決対象、打ち切りを明示します。静的分析は実行成功や収益を証明しません。

利用者のワークスペースはローカルに残ります。公開パッケージやデモはこの公開プロジェクトか合成fixtureだけを使用し、ソース本文、実名、住所、認証情報、個人のhomeパス、非公開プロジェクト成果物を公開しません。発行者名は battle-doll の別名のみです。任意のローカル推論には別の明示的同意が必要です。

単体テスト、展開パッケージ、ブラウザーの使いやすさ、実OS、ポータル確認、提出、承認、公開は別々の証拠状態です。ローカル候補を公開済みとは呼びません。この主要ガイドは5言語、既存の詳細な法律・セキュリティ・参照文書は英語・韓国語・日本語・簡体中国語です。[翻訳範囲](../TRANSLATION_COVERAGE.md)を参照してください。

## 0.8.0 の取得契約

`ontology_list_workspaces` は大規模親を `mode: "large"` で示します。`ontology_large_modules` は登録 `workspace_id` と任意の `catalog_snapshot_id`、検索語・ページ範囲を使います。`ontology_large_search` は正確な `module_roots` と `term`、`ontology_large_neighbors` は一つの `module_root` と `symbol` を受け、単一モジュール内を照会します。実際に公開された入力スキーマを確認してください。

通常ワークスペース専用 `ontology_evidence_bundle` は `workspace_id`、任意の `snapshot_id`、1–8個の `requests` を受けます。各要求は固有 `id`、`operation: "search"` または `"neighbors"` と該当操作の入力です。開始時に一度スナップショットを固定し、項目は `ok/error`、全体は `ok/partial` です。合計200結果、正規構造JSON 262144 UTF-8 byteに制限し、超過項目は安全なエラーになります。プロトコル重複テキストやwire byteはこの予算の外です。失敗した項目を成功として扱わず、カタログと通常スナップショットのIDを混在させないでください。

## バンドルの実測上の限界

Macの合成ケース（ノード1,002、関係2,000、ローカル20回）で8検索の結果を保持し、MCP要求を8回から1回に減らしました。オントロジー読み取りは8回のままです。構造化応答は32,380→33,108 bytes、ローカルp50は14.073→16.066 msに増加しました。要求の調整とスナップショットの一貫性を検証したもので、サーバー計算速度、モデル品質、他OSの性能向上の証拠ではありません。
