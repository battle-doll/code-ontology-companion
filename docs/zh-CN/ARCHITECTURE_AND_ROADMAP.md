# Code Ontology Companion：完整架构与版本路线图

[English](../ARCHITECTURE_AND_ROADMAP.md) | [한국어](../ko/ARCHITECTURE_AND_ROADMAP.md) | [日本語](../ja/ARCHITECTURE_AND_ROADMAP.md) | [简体中文](ARCHITECTURE_AND_ROADMAP.md)

## 1. 目的

Code Ontology Companion 正在向本地优先的 AI 数据管线演进：它将已授权的应用源代码、配置、构建元数据和有界运行时证据转化为可移植、可版本化的代码本体。该管线应以较低成本支持代码理解、变更影响分析、证据血缘和受到严格治理的改进工作流，同时不向 LLM 授予直接写入、部署、订单、凭据或资金权限。

版本 0.3.4 是当前公开版本：提交到 OpenAI 的 Skills-only profile 只包含确定性 Java/Spring 和 Python 静态分析、不可变本体快照、RDF 1.1 Turtle 导出、兼容 PROV-O 的血缘、离线可视化、CLI 探索，以及可选且基于同意的 Ollama 增强。只读本地 MCP 与下游项目专用扩展仅保留在完整/本地 GitHub profile 中。它尚不是下文所述的完整常驻管线。

## 2. 工程原则

- **本地优先：** 默认使用本地存储、分析、可视化和模型。外部资源仅作为由用户明确配置的可选后备方案。
- **KISS：** 即使没有图数据库、模型、守护进程或网络服务，也要使零依赖文件快照路径保持实用。
- **YAGNI：** 仅当经过验证的用例需要时，才将 Graph DB、SPARQL、REST、CI 自动化和模型安装添加为可选适配器。
- **DRY：** 维护一个规范本体和来源模型。所有存储、查询、可视化和改进组件使用同一组不可变身份与回执。
- **确定性核心：** 静态分析、指纹、候选身份、验证和提升 gate 始终保持确定性。LLM 输出仅供建议。
- **失败关闭：** 陈旧源代码、歧义绑定、畸形证据、不受支持的运行时状态、签名失败或部分变更绝不能被解释为批准。
- **面向可移植性设计：** RDF 1.1 Turtle 和有文档说明的来源信息始终是文件存储与可选本体存储之间的迁移边界。

## 3. 目标架构

```text
已授权应用
  源代码 + 构建 + 配置 + 有界运行时证据
                         |
                         v
  宿主预检与显式安装编排器
  - OS/CPU/RAM/磁盘/运行时检测
  - 发现现有 Python、Java、Ollama 和存储
  - 在任何安装或服务变更前预览并征得同意
                         |
                         v
  输入适配器
  - Java/Spring       - Python           - 未来语言适配器
  - 构建元数据        - 配置             - 经认证的只读运行时事实
                         |
                         v
  确定性分析与规范化
  - 符号、调用、导入、继承、DI/AOP/代理信号
  - 管线角色、策略叶、运行时分支、证据绑定
                         |
                         v
  规范本体与来源模型
  - RDF 1.1 / 可选 OWL profile / SHACL 验证 profile
  - observed、declared、inferred、validated、approved 证据类
  - 不可变快照、差异、血缘、发布和策略身份
                         |
          +--------------+---------------+
          |                              |
          v                              v
  默认文件快照存储                 可选存储适配器
  JSON + Turtle + 血缘             Jena/RDF4J/GraphDB/Stardog 或兼容产品
          |                              |
          +--------------+---------------+
                         |
                         v
  查询与呈现平面
  - Codex Skill/CLI       - 只读 MCP
  - 可选 SPARQL/REST      - 交互式图谱与版本比较
                         |
                         v
  可选的建议型智能
  - 发现现有本地 LLM 并由用户选择增强
  - 仅提供不含数值的假设和解释
  - inferred sidecar 与 observed 事实保持分离
                         |
                         v
  独立且受治理的改进控制器
  - 预注册候选和确定性指纹
  - 配对 replay、purged OOS、成本校准、自然 shadow 证据
  - 领域 policy gate、签名准入、CAS、canary、rollback
  - issue/PR 或策略激活仅能通过独立权限 gate
                         |
                         v
  新的 observed 结果与源代码变更返回证据管线
```

应用服务器只是此系统中的一个生产者和消费者，并非整个 AI 数据管线。Spring Boot/Tomcat 应用可以公开经认证的只读运行时事实并使用已验证策略，而本体、实验、验证和治理阶段仍保持分离。

## 4. 架构平面

### 4.1 安装与宿主发现

未来的安装编排器会先发现现有组件，再提议任何新内容。它应优先使用操作系统支持的软件包管理器和本地可用运行时。任何安装、模型下载、服务启动、端口绑定、凭据使用或外部端点均要求明确预览和用户授权。仅安装插件不得静默修改宿主。

最低 profile：

1. **公开 Skills-only profile：** 内置 Python 脚本、不可变文件、CLI 和离线工作台；不包含下游项目专用命令、策略 schema 或回执生成器。
2. **完整本地 profile：** 公开 profile 的本地能力加内置只读 stdio MCP。
3. **扩展本地 profile：** 可选图存储、SPARQL/REST 管理服务、前台或由 OS 管理的刷新触发器，以及现有本地 LLM。
4. **外部后备 profile：** 仅在本地资源不足且用户接受数据边界时，使用用户配置的远程 RDF 或模型服务。

以下仅为用户指导值，不构成严格的兼容性保证。

| Profile | macOS 指导 | Windows 指导 | 适用场景 |
| --- | --- | --- | --- |
| File-only 最低配置 | 4 个 CPU 核心、8 GiB RAM、5 GiB 可用 SSD | x64、4 个 CPU 核心、8 GiB RAM、5 GiB 可用 SSD | 不使用 Graph DB 或本地 LLM 的中小型仓库 |
| 推荐本地配置 | Apple silicon、16 GiB RAM、20 GiB 可用 SSD | 6 个或更多 CPU 核心、16 GiB RAM、20 GiB 可用 SSD | 当前 full-local workflow，并一次运行一个轻量可选服务 |
| 扩展本地配置 | Apple silicon、24-32 GiB RAM、50 GiB 或更多可用 SSD | 8 个或更多 CPU 核心、32 GiB RAM、50 GiB 或更多可用 SSD；8 GiB 或更大 GPU 为可选 | 大型仓库、RDF store 与量化 7-9B 级模型同时运行 |

低配置 PC 保留关闭 graph storage 和 model enrichment 的 file-only profile。Preflight 不得仅凭此表批准安装，而应测量实际仓库、所选模型和 store 的需求。

### 4.2 输入与语言适配器

每个语言适配器都输出规范符号和关系模型，而不是定义自己的本体。Java/Spring 分析涵盖包、类型、方法、record、导入、继承、bean 声明、注入、注解、aspect、事务、异步执行、缓存、授权、重试和代理信号。Python 分析涵盖模块、类、函数、装饰器、调用、导入、继承和数据管线角色。

未来适配器应使用有界接口来完成发现、解析、规范化、验证和能力报告。构建与配置适配器应在不执行目标代码的情况下，将源代码结构绑定到依赖版本和有效配置。运行时适配器必须经过认证、只读、清洗、受过期时间约束，并与静态证据分离。

### 4.3 规范本体

RDF 1.1 Turtle 仍是可移植性基线。完整设计可以添加有文档说明的 OWL profile 以实现可互操作语义，并添加 SHACL shape 用于制品验证；但推理器输出不得成为 observed 事实。所有推断均保留其生产者、算法或模型身份、源快照、时间戳和验证状态。

来源模型连接：

```text
源代码 revision
  -> 本体快照
  -> 假设
  -> 候选与 policy pack
  -> 数据集、replay、OOS、成本和 shadow 证据
  -> verdict 与 admission receipt
  -> canary 或 deployment
  -> observed outcome
  -> rollback 或下一次实验
```

这是支持“由于某日的订单策略改进，止损线从 2% 改为 3%”等陈述的基础，同时保留该陈述属于 observed、inferred、validated 还是 approved。

### 4.4 存储与查询

文件存储仍是默认选择，因为它可移植、可检查、便于备份且无需服务。可选存储适配器把同一份 Turtle 和来源信息导入兼容 RDF 的图数据库。特定存储的索引、推理扩展、认证、端口和许可证不属于规范模型，必须显式配置。

查询能力分层演进：

- 确定性的 CLI search、impact、history、diff 和 lineage；
- 仅限已注册工作区的只读 MCP；
- 用于标准图查询的可选 SPARQL；
- 可选的 localhost REST 管理和健康 API；
- Codex 通过有界确定性工具进行自然语言编排。

自然语言输出绝不会提升证据强度。

### 4.5 刷新与数据管线

刷新管线使用私有源指纹跳过未变化工作，在 staging 中构建已变更分析，验证每个制品，以原子方式提升不可变快照，并在失败时保留最后一个已知良好的快照。

完整设计将添加：

- 感知语言的按文件增量解析；
- 显式 Git hook、CI 或前台 watcher 触发器；
- 防抖和 single-flight lease；
- 构建/配置/运行时证据适配器；
- 绑定来源的部分刷新和依赖失效；
- 不重复发布快照或血缘的重试机制。

不会静默安装永久 watcher 或守护进程。

### 4.6 本地 LLM 边界

确定性本体不需要 LLM。明确启用后，系统会发现符合条件的现有本地模型，要求用户选择模型，仅发送有界可移植元数据，并将规范化建议存储为独立的 inferred 证据。

未来安装程序可在检查 CPU、GPU、内存、磁盘、操作系统、许可证和来源后，建议合适的本地模型。下载或启动该模型仍需明确同意。远程/云模型仅作为可选后备，绝不能静默选用。

LLM 可以：

- 总结结构变化；
- 提出不含数值的假设；
- 解释确定性判定；
- 建议调查目标。

LLM 不得：

- 伪造 observed 证据；
- 选择候选值或候选排序；
- 签名、批准、提升、部署或提交订单；
- 放宽安全、对账、幂等、成本或 OOS gate。

### 4.7 改进自动化边界

Code Ontology Companion 始终是面向读取的知识与证据组件。独立的改进控制器负责实验及任何写入工作流。特定领域的 experiment、policy、deployment 或 trading stack 是位于独立项目中的 downstream extension。此类扩展使用带版本的 evidence contract，并定义自己的 deterministic evaluation、admission、canary 和 rollback gate；它们不属于 Companion core 或公开 roadmap，也不会随 OpenAI Skills-only profile 托管。

完整/本地 GitHub profile 可以为一个受限的下游集成在策略叶和静态生产分支之间生成狭义不可变绑定；公开 Skills-only profile 不包含该命令、项目策略 schema 或回执生成器。即使在完整/本地 profile 中，该回执也不能证明运行时执行、安全性或盈利能力，更不授权修改策略、提交订单或转移资金。

## 6. 版本路线图

该路线图仅说明方向，并非日期承诺。每个版本无需依赖后续阶段即可保持实用和安全。

### 0.3.3：多语言文档与发布连续性

- 发布完整架构与版本路线图；
- 提供英语、韩语、日语和简体中文文档入口；
- 保持英语为法律和政策文档的权威来源；
- 添加文档一致性检查并保持确定性打包。

### 0.3.4：公开 profile 边界

- 将 OpenAI Skills-only 提交制品限定为通用代码本体工作流；
- 从公开制品与上架信息中排除下游项目专用命令、策略 schema 和回执生成器；
- 在完整/本地 GitHub profile 中保留已存在的可选扩展，并明确它不授予运行时、策略写入、订单或资金权限；
- 以失败关闭的制品扫描防止不同 profile 的能力声明或实现意外混入。

### 0.4.x：易用性与分析器适配器

- 提取明确且有界的语言适配器契约；
- 改进安装诊断、进度报告和可操作的失败信息；
- 改进前台 watcher 控制、防抖和 single-flight 行为；
- 提供更清晰的静态置信度和不受支持运行时指示；
- 保持零依赖默认模式。

### 0.5.x：可选存储与查询扩展

- 围绕 RDF 1.1 导入/导出定义图存储适配器契约；
- 支持由用户选择的 Jena、RDF4J、GraphDB、Stardog 或兼容存储，不强制使用任何单一产品；
- 添加可选 SPARQL 和 localhost REST 管理 profile；
- 改进大型图谱可视化和多快照比较；
- 继续完整支持文件快照存储。

### 0.6.x：本地 AI 数据管线运营

- 添加显式 Git、CI 和托管本地刷新触发适配器；
- 实现感知语言的按文件增量失效；
- 添加构建元数据、依赖、有效配置和经认证的只读运行时证据适配器；
- 添加持久的管线健康、恢复和血缘回执；
- 提供基于同意、给出本地优先建议的宿主安装助手。

### 0.7.x：受治理的改进集成

- 为外部实验控制器定义稳定的证据契约；
- 将本体身份连接到假设、候选、replay、OOS、成本和自然 shadow 回执；
- 通过另行授权的适配器支持准备 issue 或 draft PR；
- 使代码合并、部署、策略变更和运行时执行始终位于 Companion 权限之外。

### 0.8.x-0.9.x：生产强化

- 验证跨平台锁、路径安全和服务生命周期适配器；
- 添加签名证据和过期契约；
- 验证与外部控制器的 CAS、canary、rollback 和混合状态恢复集成；
- 对大型仓库和图存储进行基准测试；
- 完成迁移和向后兼容工具。

### 1.0：完整产品标准

仅当下列各项都得到独立验证后，才应宣布版本 1.0：

1. 语言适配器、构建/配置输入和经认证的运行时证据共享同一规范本体身份；
2. 文件存储和至少一种可选标准 RDF 存储可以往返转换，且不丢失可移植语义或血缘；
3. 前台、Git/CI 和经批准的托管本地刷新路径均可靠、可观察、幂等且可恢复；
4. MCP、SPARQL/REST profile、自然语言编排和可视化保持相同的读取与证据边界；
5. 可以发现现有本地模型并安全增强，同时可选安装始终明确且考虑许可证；
6. 外部改进控制器可以使用经认证的证据，并证明所有所需验证、CAS、canary 和 rollback gate；
7. 安装和升级能保留用户数据、rollback 血缘、隐私、可移植性和实用的零依赖模式；
8. 产品文档与核心工作流均以英语、韩语、日语和简体中文维护。

## 7. 兼容性与迁移

- 稳定的 `co:` 命名空间和 RDF 1.1 导出是迁移契约。
- 新存储适配器必须导入现有 Turtle，而不是创建专有事实来源。
- 快照和来源标识符不可变；适配器可以建立索引，但不得重写。
- 分析器、Companion、schema、canonicalizer 和 inference 版本始终在回执中明确记录。
- 当新分析器要求刷新时，旧快照仍应可读。
- 特定存储的功能必须具备可移植后备方案，或明确标记为不可移植扩展。

## 8. 永久安全与隐私边界

本项目从不把代码访问权视为执行目标代码、读取机密、上传仓库、修改策略、部署软件、提交订单或转移资金的许可。确定性分析排除敏感路径和生成路径，可移植制品省略绝对路径和私有指纹，可选 LLM 数据保持有界并单独分类。

自动改进是由多个经过独立验证的组件组合而成，不是本体插件内部的功能开关。任何路线图里程碑都不得仅为简化自动化而削弱这种分离。

## 9. 发布策略

版本 0.3.2 是最初的稳定功能基线，版本 0.3.3 保留为多语言文档里程碑，版本 0.3.4 则建立公开 Skills-only 与完整/本地 GitHub profile 的明确边界。后续通过兼容的 patch 和 minor 版本持续演进。不要等完整目标架构完成后才收集真实用户反馈。不要把当前产品宣传为图数据库、实时运行时跟踪器、自主重构系统、部署代理或盈利引擎。

预期产品描述为：

> 为已授权的 Java/Spring 和 Python 仓库构建并维护注重隐私的本地代码知识图谱，提供可移植 RDF 血缘、静态影响探索、版本比较和离线可视化。
