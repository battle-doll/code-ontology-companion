# 새 모델 환경의 사용 흐름 — 0.8.0

## 사용자의 모델 선택 유지

GPT-6 Astra와 GPT-6.1 Sol은 호스트에 실제 노출된 도구로 동일한 제한된 소스 근거를 사용할 수 있습니다. 사용자가 선택한 모델과 추론 강도를 유지합니다. 플러그인은 모델을 선택하지 않으며 특정 모델·원격 API·유료 계정을 요구하지 않습니다. 조회 계약 개선을 모델 성능 우위로 단정하지 않으며 모델 A/B 결과를 주장하지 않습니다.

## AI: 로컬 MCP와 고정된 근거

Windows·macOS·Linux에서 기존 Python 3.9+를 사용합니다. 공식 Skills-only 패키지에는 분석기·오프라인 HTML·로컬 MCP 설정 안내가 있습니다. 로컬 stdio 서버는 같은 버전의 전체 패키지를 사용하며 호스팅 엔드포인트가 필요하지 않습니다. 요청된 로컬 설정만 변경하고 다른 설정을 보존한 뒤 새 호스트 프로세스에서 실제 도구 노출을 확인합니다. 파일 설치만으로 MCP가 즉시 호출 가능해지지는 않습니다.

등록된 작업공간과 소스 최신성을 먼저 확인합니다. 전체 패키지는 기존 작업공간·상태·검색·관계·이력·변경·계보 7개와 `ontology_large_modules`, `ontology_large_search`, `ontology_large_neighbors`, `ontology_evidence_bundle`을 합친 읽기 전용 11개 도구를 제공합니다. 일반 작업공간은 관련 조회의 스냅샷을 고정하고 집중된 질문에는 근거 묶음을 사용합니다. 큰 프로젝트는 모듈 목록을 읽고 하나의 카탈로그를 고정한 뒤 정확한 모듈 루트로 검색하고 선택한 단일 모듈 안의 경로를 조회합니다. 카탈로그 조회는 모듈 간 호출을 해석하지 않습니다.

초기화·갱신은 별도 승인된 CLI 쓰기로 유지합니다. MCP는 임의 경로 대신 등록 ID를 받고 설치·갱신·대상 실행·소스 업로드를 하지 않습니다. 페이지·탐색 제한은 결과의 한계로 표시합니다.

## 사람: 오프라인 HTML 탐색

`graph.html`을 로컬에서 엽니다. 모듈 요약 지도에서 시작하여 심볼을 검색·선택하고 소스 위치와 관계 근거를 확인합니다. 구조·영향·변경은 서로 다른 질문을 다룹니다. 검색과 페이지별 텍스트로 접히거나 화면 밖에 있는 항목까지 접근할 수 있습니다. 보이는 수는 표시 범위이며 코드 전체를 뜻하지 않습니다.

표시 레이어와 1·2·3차 호출 강조는 독립적입니다. 레이어를 하나씩 추가하고 4차 이상 확장에서는 확인합니다. 카메라 초점·확대·Shift 끌기 이동은 별도로 사용합니다. 공간 탐색이 어려우면 키보드·동작 줄이기·텍스트 목록 대안을 사용합니다. 집계와 카메라 움직임은 새로운 소스·런타임 근거가 아닙니다.

## 근거·개인정보·검토

소스 관계 `observed`와 제안 `inferred`, `runtime_unknown`을 구분합니다. 소스 경로·행과 핵심 규칙 근거를 인용하고 최신성·파서 범위·미해결 대상·결과 제한을 표시합니다. 정적 분석은 운영 성공이나 수익을 입증하지 않습니다.

사용자 작업공간은 로컬에 남습니다. 공개 패키지·데모에는 이 공개 프로젝트 또는 합성 fixture만 사용하고 소스 본문·실명·주소·인증정보·개인 home 경로·비공개 프로젝트 산출물을 게시하지 않습니다. 배포자 표기는 battle-doll 닉네임만 사용합니다. 선택적 로컬 추론은 별도 명시적 동의가 필요합니다.

단위 테스트·추출 패키지·브라우저 사용성·실제 OS·포털 검사·제출·승인·게시는 각각 별도 증거입니다. 로컬 후보를 게시 완료라고 부르지 않습니다. 이 핵심 가이드는 5언어이며 기존 상세 법률·보안·참조 문서는 영어·한국어·일본어·중국어 간체입니다. [번역 범위](../TRANSLATION_COVERAGE.md)를 확인하세요.

## 0.8.0 조회 계약

`ontology_list_workspaces`는 대규모 부모를 `mode: "large"`로 구분합니다. `ontology_large_modules`는 등록 `workspace_id`와 선택 `catalog_snapshot_id`, 검색어·페이지 범위를 사용합니다. `ontology_large_search`는 정확한 `module_roots`와 `term`을 받고, `ontology_large_neighbors`는 하나의 `module_root`와 `symbol`을 받아 단일 모듈 안에서만 조회합니다. 실제 노출된 입력 스키마를 확인하세요.

일반 작업공간 전용 `ontology_evidence_bundle`은 `workspace_id`, 선택 `snapshot_id`, 1–8개 `requests`를 받습니다. 각 요청은 고유 `id`, `operation: "search"` 또는 `"neighbors"`와 해당 조회의 입력을 가집니다. 시작 시 스냅샷을 한 번 고정하며 항목은 `ok/error`, 전체는 `ok/partial`입니다. 총 결과 200개와 정규 구조 JSON 262144 UTF-8 byte로 제한하고 초과 항목은 안전한 오류로 처리합니다. 프로토콜의 중복 텍스트·wire byte는 이 예산 밖입니다. 실패한 항목을 성공한 답으로 취급하지 말고 카탈로그와 일반 스냅샷 ID를 혼용하지 마세요.

## 묶음 조회 실측 한계

Mac 합성 사례(노드 1,002개, 관계 2,000개; 로컬 20회)에서 검색 8개의 결과를 보존하며 MCP 요청을 8회에서 1회로 줄였습니다. 온톨로지 읽기는 8회로 유지됐습니다. 구조화 응답은 32,380→33,108 bytes, 로컬 p50은 14.073→16.066 ms로 늘었습니다. 요청 조율과 스냅샷 일관성의 검증이며 서버 계산 속도·모델 품질·다른 OS의 성능 향상 증거가 아닙니다.
