# Участие в разработке

[English](../../CONTRIBUTING.md) | [한국어](../ko/CONTRIBUTING.md) | [日本語](../ja/CONTRIBUTING.md) | [简体中文](../zh-CN/CONTRIBUTING.md) | [Русский](CONTRIBUTING.md)

Изменения должны сохранять детерминизм, локальную обработку и минимальные полномочия по умолчанию.

## Локализация документации

При изменении документа обновите соответствующие английскую, корейскую, японскую, китайскую упрощённую и русскую версии в том же изменении. Выполните `python3 scripts/validate_documentation.py`. Переводы политики конфиденциальности, условий, товарных знаков, NOTICE и сторонних уведомлений информационные и сохраняют общий маркер приоритета английского оригинала. Не переводите и не заменяйте `LICENSE` и лицензии сторонних зависимостей.

Перед предложением изменения:

```bash
python3 -m unittest discover -s tests -v
python3 scripts/validate_package.py
```

## Версия и выпуск

Каждое отслеживаемое изменение выпуска требует новой версии продукта A.B.C и датированной записи в `CHANGELOG.md`. A обозначает совершенно другой продукт, B — крупное изменение того же продукта, C — частичное улучшение или исправление функций. Само добавление возможности не требует увеличения B. Текущая работа сохраняет серию 0.8.x. CI сравнивает PR с базовой веткой, а push в main — с предыдущей ревизией; кандидат должен превышать каноническую базовую версию, а датированная запись должна стоять первой. Только явно зафиксированный неопубликованный кандидат 0.9.0 соответствует базовой версии 0.8.2; произвольное понижение версий запрещено. Опубликованные теги, хеши коммитов, идентификаторы архивов и исторические свидетельства сохраняются.

Перед публикацией:

1. Синхронизируйте версию в manifest, константах, SBOM, eval-метаданных, валидаторах, путях CI, тестах и актуальных документах.
2. На окончательном коде выполните весь набор тестов и проверку пакета.
3. Дважды соберите оба детерминированных профиля и сравните байты и контрольные суммы.
4. Обновите зарегистрированную собственную онтологию плагина из финального закоммиченного кода; добавьте declared-событие политики версий и validated-событие подтверждённых проверок.
5. Создавайте тег только после финального коммита и обязательных проверок CI. Никогда не перемещайте опубликованный тег.

Используйте только синтетические fixtures. Не коммитьте частные репозитории, сторонние исходные фрагменты, учётные данные, онтологии реальных закрытых проектов, веса моделей или скопированные проприетарные схемы.

Новые сетевые возможности, выполнение целевого кода, установка пакетов, аутентификация, телеметрия, постоянные сервисы, hooks, записывающий MCP, внешние базы и автоматическое скачивание моделей требуют отдельного проекта и обновления документов privacy, security, threat model, тестов, SBOM и submission review.

Предоставляя изменение, участник подтверждает право лицензировать его по Apache-2.0.

## Личность издателя перед открытым рассмотрением

В исходных и релизных метаданных используйте только псевдоним battle-doll и защищённый адрес коммита. GitHub способен создать временный merge-коммит PR с адресом аккаунта независимо от локальной настройки Git. Проверяйте конфиденциальность почты аккаунта до создания публичного PR. Запуск workflow непосредственно на ветке позволяет проверить кандидата без такого временного merge-ref. Проверки исходников, выбранной истории и ZIP всё равно обязательны.

## Защита персональных данных и доказательства публикации в 0.8.3

Настроенный закрытый профиль HMAC-SHA256 позволяет отклонять выбранные идентифицирующие строки в поддерживаемых артефактах и ответах ИИ без сохранения настоящих имён или личных адресов электронной почты в публичном исходном коде. Ключ и отпечатки профиля должны находиться вне защищаемых исходных и выходных каталогов; профиль никогда не является публичным артефактом. Для публичного экспорта обязателен подходящий непустой защищённый профиль; обычное локальное исследование может работать без него. Отсутствие необязательного профиля не подтверждает защиту имён. Ограниченные проверки текста и кодировок не обнаруживают все неизвестные имена, произвольные двоичные метаданные, содержимое изображений или вывод сторонних программ.

В POSIX проверяются владелец и права файла, включая повторную проверку во время чтения. В Windows профиль проверяется по реальному открытому дескриптору: владелец должен совпадать с текущим пользователем, а действующие разрешения доступа допускаются только для него, Local System и встроенной группы Administrators. Неизвестные ACE, пустой указатель DACL и непроверяемые права приводят к отказу. Реализация и синтетические тесты не заменяют проверку на настоящей Windows.

Перед публичным PR требуются свежая доверенная проверка конфиденциальности электронной почты реального аккаунта GitHub и аудит всех выбранных ссылок на исходные и созданные провайдером коммиты. Локальные настройки Git, заявления пользователя, тестовые примеры и проверка только HEAD не заменяют подтверждения провайдера. Старые ссылки, сохраняемые провайдером, считаются нерешённым риском до подтверждения удаления. Публикация допустима только с публичным именем разработчика battle-doll без личных данных. Проверки не добавляют передачу личности, телеметрию или отдельный HTML-отчёт.

См. [руководство по защите данных](PRIVACY_OPERATIONS.md). Тесты, проверка провайдера, загрузка, отправка на рассмотрение, одобрение и публикация — разные состояния доказательств.
