# Цикл качества и точная передача — 0.9.3

[English](../QUALITY_0_9_3.md) | [한국어](../ko/QUALITY_0_9_3.md) | [日本語](../ja/QUALITY_0_9_3.md) | [简体中文](../zh-CN/QUALITY_0_9_3.md) | [Русский](QUALITY_0_9_3.md)

Разработчик: battle-doll. Сохраняются локальный MCP, автономный HTML для людей, пять языков, Windows, macOS и Linux.

## Текущий публичный human-вид исходного конвейера

Публичные `analyze`, `refresh` и обычный `pipeline-html` по умолчанию используют ограниченный human-обзор: область → основной структурный модуль → краткий обзор, глубина по умолчанию2, максимум3. На экране не более32 узлов и64 агрегированных связей; пять языков UI разделяют локальные script chunk, поиск ограничен текущей страницей. Общий режим возвращает к корню всей области, сброс камеры не меняет область. Карточки исходных политик — opaque основания со смыслом UNKNOWN, а не полное естественно-языковое описание условий, расчётов и исключений. Точные глубокие данные остаются вMCP. `--presentation records`, legacy workbench и явный partitioned record export сохраняются отдельно; не каждый business export становится human-обзором. Абстракция HTML не разрешает удалять смысл, необходимый ответу или политике. Приватность, ACL, текущая привязка исходника и проверки инвалидирования обязательны.

## Повторяемый процесс от фактов к тексту политики

До prose создайте worksheet фактов со snapshot/ID оснований и evidence mapping каждого обязательного и уже поддержанного факта. Сохраните все операнды условий, AND/OR, ветви true/false, ранние выходы, единицы, формулы, округление, исключения, полномочия, владение, ID, состояния, точные временные границы (`<` против `<=`) и восстановление. Перечисляйте замкнутые множества; явно отмечайте скрытое, неподдержанное и UNKNOWN, не угадывая значения и не считая их отсутствующими. Классифицируйте guard по реальному `controlFlow.kind`: `synchronized`, `try`, `if`, `switch` не являются loop; так можно называть только реальную итерацию.

Разделяйте документальный контракт и принудительное обеспечение реализацией, статические наблюдения и runtime-основания. После проверки обязательств превращайте worksheet в prose и сверяйте в обе стороны: каждое утверждение с основанием и каждый обязательный факт с текстом. Извлечённая worksheet не является полным рассказом политики. Абстракция HTML не оправдывает потерю обязательного смысла. Раздельно ведите шесть измерений: обработка файлов, декларации/типы, exact calls, семантика политик, доставка MCP и coverage документа; сохраняйте исходные знаменатели, ошибки, пропуски, UNKNOWN без смешивания сумм или произвольных частичных баллов.

Сохраняйте evidence mapping поддержанных фактов для предотвращения регрессий. Повторное использование проверки допустимо только при доказанном точном равенстве hash и затронутой области/достижимости с явными parent/new consumer pins; иначе перепроверьте изменённую область. Равенство hash не отменяет приватность, ACL, привязку исходника и инвалидирование. Этот общий процесс не создаёт ответы для конкретного приложения, runtime-утверждения или дополнительную поддержку parser.

Списки сырых выражений, opaque-названия guard и позиционные constructor tuple не становятся человеческим смыслом политики автоматически. До prose свяжите доказанные declaration/constructor/component/accessor/helper/provider bindings с именованными ролями параметров и полей результата, полностью уточнив состояния, эффекты, предпосылки, полномочия и исключения; необъявленные единицы/эффекты остаются UNKNOWN. Классифицируйте факты: ESSENTIAL → абзац основного текста, SUPPORTING → машинный индекс, ALREADY_COVERED → конкретный абзац, UNKNOWN → явная причина. Не заменяйте политику дампом всех AST node и не теряйте существенное молча при абстракции. Намерение документа, статические основания и runtime-обеспечение различаются.

**Область legacy / явно выбранного records workbench** — HTML использует общие страницы исходных записей в `data/` для всех пяти языков. Автономный скрипт обеспечивает удобный просмотр JSON и поиск значений; при ошибке загрузки остаётся статическая ссылка на JSON. Все записи, привязки к исходнику, проверки приватности и ограничения объёма сохраняются. Храните всю экспортированную папку вместе.

Глубокие поля JSON могут использовать `companion.flat-json.v1`. Восстановите `root` по упорядоченным `nodes` и ссылкам `$ref`, проверьте `originalSha256` и `sourceBinding`. ID, доказательства и пагинация сохраняются. Это передача без потерь, а не новый анализ или разрешение. Ограничения байтов, узлов, глубины и приватности сохраняются.

Объявления Java сохраняют аргументы обобщённых типов, аннотации, throws и отдельные диапазоны заголовка, объявления и тела. Для каждого типа указываются исходная форма, разрешённый тип либо null и причина. Даже если уникальное объявление позволяет связать статический вызов, неразрешённые сведения о типах сохраняются. Неоднозначные кандидаты не считаются точными вызовами; статическое разрешение не доказывает выбор реализации во время исполнения.

Фрагменты политик сохраняют поддерживаемый контекст управления и порядок действий. Непрозрачные литералы, неизвестные вызовы, динамическая диспетчеризация и неизвестные единицы остаются явными. Синтаксис сам по себе не доказывает исполнимость, утверждение или полноту бизнес-правила.

Чувствительные выражения могут сохранять структуру вызовов, ссылок, присваиваний и управления с `structuralOnly`, заменяя числа, значения в кавычках и логические значения на `masked_value`. Null остаётся лишь маркером исходника. Вложенные отложенные тела наследуют чувствительный контекст. Эти фрагменты остаются частичными, без подтверждения значений, стандартных API, единиц и формы записей. Маскированное значение нельзя считать нулём, false, пустой строкой или поводом восстанавливать его содержимое.

Поддерживаемые операции библиотек Java получают `expression.staticContract` только при наличии статических доказательств типа и перегрузки стандартной сигнатуры. Ищите `contractId` в `standardApiContracts` того же фрагмента, а не как отдельную запись. Каталог фиксирует арифметику, округление, единицы и исключения со ссылкой на первичную спецификацию, но не доказывает значения, выполнение или динамическую диспетчеризацию. Связи конструкторов enum сохраняют порядок аргументов и прямые присваивания полям; неоднозначные и условные связи остаются кандидатами.

Для выбранного и доступного Java `record` неявный аксессор компонента без аргументов может передать объявленный статический тип результата, если подтверждены получатель, тип компонента, диапазон исходника и свидетельства объявления. `staticAccessorBinding` сохраняет свидетельства компонента; явно объявленный аксессор без аргументов имеет приоритет. В цепочках результатов компонентов и фабрик проверяется доступ из пакета и внутри охватывающего верхнеуровневого типа вызывающего кода. Неподдерживаемые обобщённые и локальные record, недоступные типы, затенение имён и неоднозначность остаются UNKNOWN. Эта связь типов не добавляет точных рёбер `CALLS` и не доказывает значения компонентов, динамическую диспетчеризацию или выполнение.

Получайте все страницы MCP зафиксированного снимка. При превышении лимита байтов уменьшайте страницу, не считайте ошибку успешным пустым ответом. Оставляйте невыданные ID в знаменателе, восстанавливайте плоские записи перед чтением вложенных условий и запрашивайте доказательства мест вызова, на которые ссылаются типовые контракты. Этот набор ссылок не является знаменателем всех вызовов исходного кода.

До вывода об отсутствующей ссылке проверяйте вложенные `references[].declarations[]`. Лексический идентификатор параметра может быть определён там вместе с диапазоном исходника и типом, не являясь отдельно запрашиваемой записью. Ссылайтесь на содержащий его фрагмент MCP и отличайте отсутствие определения от неизвестного значения параметра во время исполнения.

Зафиксировать хеши, состав и критерии → создать знания → получить реальные страницы MCP → написать документ только по онтологии → независимо сравнить с критериями из исходников → воспроизвести синтетическими тестами → исправить продукт → повторить на тех же входах. Сохраняйте отдельные примеры, не использованные для исправления.

Отдельно отчитайте файлы, объявления и типы, точные вызовы, семантику политик, передачу MCP и полноту документа. Сохраняйте ошибки в исходном знаменателе. Не присваивайте частичным описаниям полбалла и не учитывайте дополнения из исходников как успех онтологии. Изменения исходника, снимка, анализа, модели/запроса или документа требуют повторной проверки. UNKNOWN/PARTIAL являются допустимыми результатами.

Необязательный частный контракт `companion.reviewed-literals.v1` сохраняет независимо проверенные несекретные значения политик. Выберите его явно: `analyze --literal-review FILE` или `refresh --literal-review FILE`. Контракт связывает отпечаток исходников, хеш файла и точный диапазон байтов UTF-8 с хешем токена; глобальные списки разрешённых строк не принимаются. Частная рабочая область хранит контракт для обновления и восстановления. Изменение входа блокирует повторное использование до новой проверки либо явного удаления через `refresh --clear-literal-review`. Проверки приватности и чувствительного контекста продолжают действовать. Каждый запрос остаётся разрешённым, отклонённым или ненаблюдаемым; разрешение не доказывает полноту извлечения или документа. Метаданные — ввод доверенного вызывающего, а не удостоверение личности или право публикации. Удаление контракта влияет на будущие снимки; существующие снимки и экспортированные копии сохраняют содержимое.

Верхние поля: `format`, `purpose` (`private-policy-analysis`), `sourceFingerprint`, `review`, `entries`. В `review` находятся `reviewId`, `reviewerKind` (`independent_source_review`) и `reviewedAt`. Каждый элемент содержит `path`, `sourceSha256`, `tokenByteStart`, `tokenByteEnd` (исключая конец), `tokenSha256`, `classification` (`nonsecret_policy`), `reasonCode`, `usageContext`, `reviewId`. Диапазон включает кавычки; коды причины и контекста не содержат исходных значений. При активной проверке непроверенные значения в кавычках остаются скрытыми, включая числовые строки прежнего типизированного извлечения десятичных значений. Храните файл приватно. CLI не выводит разрешение из текста исходника и не ищет контракт автоматически.

Инициализаторы массивов и аргументы аннотаций сохраняют порядок, структуру исходного кода и подтверждения проверки точных вхождений. Цель аннотации служит свидетельством объявления в коде; применимость, маршруты фреймворка и поведение во время выполнения остаются UNKNOWN. В структурном фрагменте с чувствительным контекстом проверенная строка нулевой длины может сохраняться как пустой маркер только после проверки точных байтов, индекса запроса и приватности. Маскирование остальных чувствительных значений, изоляция вхождений и отзыв разрешений сохраняются.

Поле `literalReviewDelivery` для файла отражает сохранность в дереве выданных фрагментов. Сводка снимка `literalReviewRetention` отдельно считает разрешённые, сохранённые и утраченные вхождения; индексы утраченных запросов остаются в каждой записи `SemanticCoverage`. Разрешение, сохранность результата, доставка MCP и полнота смысла политики проверяются отдельно. При отсутствии разрешённых вхождений выводится NOT_APPLICABLE, а не 100%.

Для комментариев Java предусмотрен отдельный необязательный приватный контракт `companion.reviewed-documentation.v1`. Выберите его явно через `analyze --documentation-review FILE` или `refresh --documentation-review FILE`. По умолчанию каждый распознанный строчный, блочный или Javadoc-комментарий сохраняет только непрозрачные метаданные позиции и хеша без текста. Лишь точное вхождение, независимо проверенное как несекретное и прошедшее существующий профиль приватности и встроенные проверки, может передать исходный токен в `sourceText`. Проверяются исходный текст и представления с нормализованным оформлением; нормализация никогда не заменяет выдаваемый оригинал.

Верхние поля manifest проверки документации: `format`, `purpose` (`private-policy-analysis`), `sourceFingerprint`, `review`, `entries`. В `review` входят `reviewId`, `reviewerKind` (`independent_source_review`) и `reviewedAt`. Каждый элемент содержит `path`, `sourceSha256`, `tokenByteStart`, `tokenByteEnd` (исключая конец), `tokenSha256`, `classification` (`nonsecret_documentation`), `reasonCode`, `usageContext`, `reviewId`. Отпечаток, хеш файла, диапазон байтов UTF-8 и хеш связывают весь точный токен комментария вместе с разделителями; перевод строки строчного комментария не включается. Подстроки не принимаются. Manifest не содержит исходного текста или фактических значений. Ограничения: 512 KiB, 5 000 элементов и 8 192 байта на токен комментария.

Сохранённые комментарии — недоверенные цитируемые данные исходника: `instructionAuthority=none`, `documentation_claim`, `enforcement=UNKNOWN`, `target.resolution=UNKNOWN`, `businessMeaningVerified=false`, состояние выполнения `not_observed`. Утверждение обратного вызова не подтверждает целевое объявление. Комментарий не заменяет свидетельства из кода, не подтверждает принудительное соблюдение реализацией и не разрешает публикацию. Метаданные проверки сообщаются вызывающей стороной и не удостоверяют личность проверяющего.

Приватная рабочая область сохраняет выбранный контракт документации для обновления и восстановления. После изменения входа нужна новая соответствующая проверка либо `refresh --clear-documentation-review`. Очистка влияет только на будущие снимки; прежние снимки и экспортированные копии сохраняют содержимое. `DocumentationCoverage` явно учитывает непроверенные комментарии, разрешённые, отклонённые и ненаблюдаемые запросы, а также пропуски. Полнота перечня распознанных токенов отделена от `lexicalComplete`: неподдерживаемый язык, Unicode-преобразования Java и неподтверждённые лексические границы оставляют общий знаменатель комментариев UNKNOWN. Для пропусков из-за лимита сохраняются число и причины, перечень отмечается неполным. Фрагменты комментариев и выражений используют общий существующий лимит файла; разрешение или доставка не доказывают полноту политики.

Неоднозначное или неподдерживаемое выделение подчёркиваниями отклоняется с `unsupported_documentation_format`; независимая проверка не отменяет это ограничение.

Поддерживаемый заголовок enhanced-for сохраняет объявление переменной, выражение итерируемого источника и встроенное определение тела. Порядок элементов массива, условия тела, ранние выходы и кандидаты накопительных обновлений связаны с исходными позициями. Фактический обход, число итераций и достигающие значения остаются UNKNOWN. Неподдерживаемые заголовки и непрозрачные литералы отмечаются явно.

При `resolution=selected_static_final_field` поле `staticFieldBinding` связывает единственное доступное static-final поле выбранного исходного кода с фрагментами объявления и инициализации. Значение инициализатора не подставляется; выполнение инициализации не доказано. `recordConstructorDeclarations` сопоставляет аргументы неявного canonical-конструктора с позициями объявленных параметров record. Для явных и compact-конструкторов сохраняются кандидаты и неизвестность передачи значений; фиктивные точные CALLS и значения полей во время выполнения не создаются.

Документированные стандартные перегрузки включают десятичный остаток и вычитание наносекунд. Остаток может быть отрицательным и не является всегда неотрицательным modulo. MathContext ограничивает внутреннее целое частное, а само вычисление остатка точно. Временные контракты сохраняют единицы и условия исключений. Числовой тип сам по себе не определяет бизнес-единицы.

Перед отдельным запросом записей найдите определения `source-body:`, `source-binding:` и `source-record-constructor:` внутри содержащих их фрагментов. Ссылки цикла задают фрагмент определения и положение тела, ссылки конструктора — локальный каталог объявлений. Ссылкам на поля нужны реальные фрагменты объявления и инициализации. `sourceRange.charStart/charEnd` задаёт диапазон кодовых точек Unicode с нулевой начальной позицией и исключённой конечной границей; manifest проверенных литералов и комментариев использует байты UTF-8. В обоих случаях проверяйте snapshot, хеш исходного файла и наличие определений всех ссылок.

Если после итоговой проверки определение отсутствует, не совпадает или отозвано, зависимые доказательства типов, методов доступа, конструкторов и API также отзываются. Исходный синтаксис и независимые соседние доказательства сохраняются. Итоговый snapshot не допускает незавершённой проверки зависимостей; UNKNOWN не превращается в подтверждённое утверждение.

В RDF конвейера семантические фрагменты, включая покрытие, пропуски и проверенные комментарии, сохраняют тип `co:Symbol` для существующих запросов и получают тип `co:SemanticFragment` с фактическим `co:extractorVersion`. Вымышленный `ruleVersion` не подставляется. SHACL требует версию экстрактора для семантических фрагментов и по-прежнему требует `ruleVersion` для обычных символов, утверждений и правил политики. Это ограниченная проекция метаданных: AST выражений и полный текст проверенных комментариев не экспортируются в RDF целиком. Соответствие формам не доказывает полное равенство JSON/AST, полноту семантики PROV, полноту политики или выполнение во время работы. Сам экспорт не меняет статус независимой проверки RDF `not_run`.

Символы Java Record содержат `recordComponents` независимо от вызовов конструктора. Индекс, имя, объявленный тип и пара разрешённого/UNKNOWN типа связаны с ID родительской записи, путём, хешем исходного файла и диапазонами символов. `recordHeaderRange` включает скобки списка компонентов; `recordComponentCoverage` различает известное исходное число, выведенные, пропущенные и неподдерживаемые элементы. Вывод ограничен 64 компонентами, но общий парсер и существующий анализ полей и вызовов не обрезаются. Слишком длинный текст скрывается с указанием причины. Неизвестные типы остаются null/UNKNOWN, некорректные или неполные списки — PARTIAL. Значения аргументов аннотаций не выводятся. Наблюдение декларации не доказывает сохранённые значения, выполнение или дополнительные точные CALLS.

Интерпретируйте `staticFieldBinding` и `receiverStaticFieldBinding` по полю `resolution`. Для `selected_static_final_field` нужны переданные декларация исходного поля и свидетельство инициализации. Для `declared_record_component_field_type` проверяются фактический родительский Record и его декларация `recordComponents`; инициализатор и каталог вызовов конструктора не требуются, значение во время работы остаётся UNKNOWN. Привязку получателя сверяйте с `receiverStaticType`, а не с типом результата вызова. Неизвестные варианты resolution остаются неподдерживаемыми. Конфликтующие явные импорты дают тип UNKNOWN; компоненты void и varargs не в конце списка отмечаются unsupported/PARTIAL без сокращения наблюдаемого списка.

Локальные объявления Java `var` внутри блока используют только уже подтверждённый статический тип выражения инициализации, связанного с исходным файлом. `localTypeInference` связывает диапазоны объявления, инициализатора и лексической области с хешем файла; использование ссылается на определение через `localTypeBinding`. Ссылки компактны, прежний предел глубины зависимостей сохранён. Неизвестные, неверные, самоссылочные, множественные, скрытые и неподдерживаемые инициализаторы остаются UNKNOWN. Потеря или отзыв определения удаляет зависимые доказательства типа/API, сохраняя синтаксис и независимые свидетельства. Учёт выданных объявлений `var` отделён от пропусков исходного списка фрагментов. Это не вычисление значений, не доказательство определённого присваивания, общего вывода обобщённых типов или выполнения.

Повторное использование типа инициализатора требует совпадения принадлежности именованному типу и методу в лексических областях и индексе Java. Локальные и анонимные классы, отсутствующая или противоречивая принадлежность и неподтверждённые ссылки на внешнее поле остаются UNKNOWN. Проверяется ближайшее объявление члена; унаследованный член может скрывать внешнее поле. Утрата символа владельца или изменение принадлежности места использования отзывает зависимые доказательства. Неподдерживаемые области операторов сохраняются в знаменателе.

Принадлежность сверяется с реально проецируемыми определениями символов Java. sourceRange совпадает с полным declarationRange, а bodyRange задаёт тело; смещения измеряются кодовыми точками Unicode. declarationSpan охватывает всё объявление, тогда как span/headerSpan могут описывать только заголовок. Поддерживаемый controlFlow.owner.id содержит реальный идентификатор символа метода. Отсутствие определения, изменение границ, несовпадение диапазонов, подмена идентификатором другого метода или недоступность определения отзывает зависимый вывод. Совпадение копий метаданных само по себе не является доказательством.

Проверка наследуемых имён Java использует ограниченный каталог `java-se21-member-inventory-1` только при точной привязке платформенного типа. Поле `javaStaticModel` в снимке и спецификации анализа задаёт допущение Java SE 21; `actualTargetJdk` остаётся `UNKNOWN`. `platformTypeContracts` хранит без дублирования перечни полей, вложенных типов и родителей со ссылками на первичные спецификации. Краткие ссылки `platformInheritance` указывают на `platformInheritanceChecks` в том же fragment или символе Record, сохраняя идентификаторы исходных объявлений, путь, дайджест, диапазон заголовка и позиции ссылок на родителей. Поля `sourceRange` и `declarationHeaderRange` символов типов используют символьные смещения с нуля и исключённой правой границей. Это ограниченные лексические наблюдения и документированные платформенные допущения, а не обнаружение целевого JDK, полный экспорт членов, точные CALLS, выполнение или значения времени исполнения. Неизвестные родители, неоднозначные import, конфликты платформенной идентичности с выбранным исходным кодом, существующие скрывающие члены и пределы проекции сохраняют явную неопределённость. Локальные типы `var` эта модель не выводит.

Перед использованием отсутствия наследуемого имени как основания для типа или API-контракта проверяется перечень объявлений в нужном пространстве имён каждой выбранной области исходного кода. `sourceScopes[].memberInventory` отдельно хранит состояния полей и вложенных типов, число обработанных областей непосредственных объявлений (не число полей) и отсортированный список уникальных `fieldNames`. Ограниченные полные объявления полей поддерживают несколько деклараций в одном операторе; запятые параметров типа отделяются от запятых деклараций, каждый инициализатор поля должен быть полностью разобран поддерживаемой ограниченной грамматикой выражений без вычисления значений. Корректный заголовок компонентов record задаёт имена неявных полей, поддерживаемые enum-константы — имена непосредственных полей. Реальное сокрытие имени остаётся present. Поля и константы с аннотациями, неподдерживаемые или непроверяемые заголовки конструкторов, неподдерживаемые или некорректные области, границы Unicode escape и лимиты оставляют соответствующее пространство имён в состоянии `UNKNOWN`. JavaIndex, точные CALLS, значения времени исполнения и полнота всей политики не расширяются.

Полное имя родительского типа или единственный явный импорт типа позволяют закрепить известного родителя независимо от посторонних on-demand импортов. Неизвестные родители, конфликтующие явные импорты и неоднозначные незакреплённые on-demand импорты остаются `UNKNOWN`. Статические on-demand импорты родительского типа, включая выбранных владельцев, также остаются `UNKNOWN` без отдельного привязанного к исходнику доказательства отсутствия члена. Лексический вложенный тип не становится стандартным из-за похожего имени. Тип получателя из возвращаемого значения по-прежнему требует точного доступного объявления и callsite; неразрешённая перегрузка не получает стандартный API-контракт. Правила пространств имён и импортов следуют [JLS 6.5.5](https://docs.oracle.com/javase/specs/jls/se21/html/jls-6.html#jls-6.5.5) и [JLS 7.5](https://docs.oracle.com/javase/specs/jls/se21/html/jls-7.html#jls-7.5). Это ограниченные статические проверки; фактический целевой JDK, иерархия, значения и выполнение во время исполнения остаются `UNKNOWN`.

Встроенные определения платформы сопоставляются по ID и содержимому canonical JSON. Повторения с полностью одинаковым содержимым эквивалентны в пределах существующего лимита проверки в 64 записи. Порядок ключей объекта не учитывается, но порядок элементов массива и типы значений JSON различаются. При конфликте содержимого с одинаковым ID порядок массива не определяет приоритет. Зависимые подтверждения типов и API получают `UNKNOWN` с причиной `platform_inheritance_definition_conflict`, а независимые соседние подтверждения сохраняются. Исходная модель и содержимое шести canonical контрактов платформы не изменены.

Схема 2 `platformInheritance` связывает каждое место использования типа с ограниченным графом `platformTypeProofs`. Прямое подтверждение указывает фактически переданное объявление или позицию синтаксиса, владельца, запись типа, пространство имён, путь и хеш исходника. Переданное подтверждение ссылается на реальные позиции получателя, аргументов или операндов в той же записи IR; сигнатуры стандартного API и типы входов и результата проверяются по общему каталогу. Поэтому примитивный результат может сохранять основание разрешения типа получателя, не объявляя эти типы одинаковыми. Отсутствующие, конфликтующие, отозванные или неверно привязанные основания дают `UNKNOWN`; независимые соседние основания сохраняются. Канонически одинаковые дубликаты эквивалентны в прежних пределах. Проверки и подтверждения типов вместе ограничены 64 записями, а их общие каталоги и метаданные — 64 KiB. Циклы и превышения глубины или обхода не подтверждают результат. Сопоставляются диапазоны объявлений и тел типов и методов, ограниченные наблюдения import и точные ID callsite. Встроенные ID подтверждений и JSON pointer не являются отдельными запрашиваемыми записями исходника. Это статические сведения при явно заданной модели Java SE 21; фактический целевой JDK, значения, диспетчеризация, исполнение и полнота бизнес-политики остаются `UNKNOWN`.

Кэш действительности определения `platformTypeProofs` не заменяет проверку каждого фактического потребителя. Перед повторным использованием результата проверки зависимостей должны совпасть позиция в IR, роль, тип и ссылки на проверки. Действительное подтверждение другого потребителя не подходит независимо от порядка обхода.

Необязательный слой бизнес-знаний сохраняет исходный снимок и существующую 3D-карту. Отдельное автономное представление на пяти языках показывает все выбранные бизнес-записи, направленные связи, аспекты единиц, времени и композиции политик, происхождение и независимые состояния поддержки и одобрения. Отсутствующие и неподдерживаемые аспекты остаются UNKNOWN. Одобрение знания не разрешает исполнение и не доказывает поведение во время работы или полноту всей политики. Изменение исходных данных, спецификации или проверки требует повторной валидации; исходные знаменатели выбора, ошибок и пропусков сохраняются.

Экспорт бизнес-HTML или пакета требует export_html/export_bundle и одновременно read_structure, read_policy, read_evidence. Доверенные обратные вызовы под блокировкой публикации повторно проверяют точные идентификаторы исходного и бизнес-снимка, ревизию ACL, текущий профиль приватности и стабильность чтения. Создаётся новое частное дерево с каждой исходной бизнес-JSON записью и охватом, инертным текстом и относительными автономными ссылками; оно разделяет существующий общий бюджет 1 GiB с исходным экспортом. RDF 1.1/PROV и объявленная SHACL shape сопровождаются отчётом потерь отображения каждой записи со ссылками на сохранённый JSON. Сериализация или успешная shape не доказывают бизнес-истину. Проверки в нативном браузере и shape остаются NOT_RUN до отдельного выполнения. Последующие изменения ACL или отзыва не отзывают уже экспортированные копии. Разработчик: battle-doll.

Ограниченный парсер TypeScript boolean-политик сохраняет чистую типизированную функцию рядом с именованным пустым классом или полями `boolean`, `number`, `string` без начальных значений и с завершающей точкой с запятой. Поддерживается необязательный `export` непосредственно перед классом. Класс разбирается и сохраняется как привязка модуля: совпадения имён классов и функций и затенение внутренних имён типов не игнорируются. Инициализаторы, static-блоки и члены, методы, наследование, decorator, вычисляемые имена и другие неподдерживаемые формы остаются `UNKNOWN`; класс не удаляется из выбранного исходника. Запись `source_policy_declaration` использует `source-policy-declarations-1` и сохраняет путь, хеш исходника, диапазон строк, диапазон индексов токенов lexer, статус неполитического объявления и ограничения исполнения. Это наблюдение объявления, а не подтверждение исполняемой формулы политики или значения поля во время выполнения. Отдельный `sourceDeclarationCoverage` сохраняется в запечатанных сводках и MCP, не увеличивает число правил и не доказывает полноту бизнес-политики. Прежние бюджеты сохраняются; пропуск записей объявлений блокирует публикацию нового снимка. Символьные и байтовые offset не заявляются.

Свидетельство типа локальной переменной `var` может сохранять ограниченные свидетельства наследования платформы через точную запись инициализатора. Прямое происхождение `kind=local_initializer` в `platformTypeProofs` указывает на фактически выданное локальное объявление и его доказательство `/expression/staticType`; каждое место использования сохраняет отдельный ID доказательства. Необходимые определения проверок и каталога передаются без дублирования в прежних пределах. Проверяются также фактическая привязка переменной, диапазоны объявления и использования и владелец метода. Отсутствующие, отозванные, конфликтующие или превышающие лимит зависимости остаются `UNKNOWN`, а структура исходного кода и покрытие сохраняются. Это композиция статических типов, а не подтверждение значения во время исполнения, успешного исполнения или точного разрешения вызова.

Отдельный учёт объявлений передаётся из запечатанной сводки политик в исходный HTML, охват бизнес-кандидатов, MCP только для чтения и бизнес-HTML. Проверка и отзыв сохраняют исходный знаменатель. Отсутствующий учёт старой версии или языка, отличного от TypeScript, обозначается UNKNOWN, а не выдуманным нулём. Передаются только фиксированные коды области и причин, неотрицательные целые счётчики и явные флаги полноты. Перечень объявлений не увеличивает число правил политики и не доказывает полноту бизнес-политик.

Перечень непосредственных полей также отклоняет зарезервированные идентификаторы объявлений, повторяющиеся или конфликтующие модификаторы, некорректные wildcard bound, отсутствующие инициализаторы и лишние конечные токены. Аргументы enum и заголовки компонентов record имеют ту же консервативную границу синтаксиса. Повторное использование общего парсера выражений не заменяет javac: непустые anonymous-тела членов, неподдерживаемые типизированные, аннотированные, вложенные или не полностью разобранные лямбды, аргументы generic method и различия грамматики, не сохранённые ограниченным IR, остаются UNKNOWN. Поэтому даже близкий корректный синтаксис может быть отложен с явной причиной inventory. Структура строковых и символьных literal проверяется без сохранения значений. Это проверка поддерживаемого синтаксиса объявлений; корректность compiler, совместимость типов присваивания, выполнение и фактический целевой JDK не проверены.

При наличии точного диапазона исходного объявления владельцу потока управления добавляется отдельный declarationSpan. Прежний лексический span сохраняется; аннотации и многострочный заголовок могут расширять полное объявление. Оба диапазона связаны с тем же хешем исходника и символьными позициями. Это уточняет происхождение позиций, не добавляя объявления, вызовы, смысл политики или свидетельства исполнения. Для неразрешённых лексических владельцев диапазон не выдумывается.

## Разделённое хранение бизнес-кандидатов

По умолчанию генерация обходит весь выбранный снимок исходных записей. Неизменяемые сегменты SQLite содержат не более 10 000 строк и 64 МиБ каждый и укладываются в прежние бюджеты количества записей, вывода и времени рабочей области. Ограничения записи, глубины JSON, запросов, приватности и доступа сохраняются. Явный --max-records задаёт ограниченный просмотр с исходным знаменателем и состоянием каждого пропущенного входа. --partition-size задаёт число строк сегмента. Проверка ограничена 10 000 понятиями на запрос и сохраняет всю автоматическую основу, независимые квитанции и знаменатель sourceCandidates. Обязательны фиксация исходника, спецификации и прав, блокировка публикации, сравнение указателя и атомарная публикация. Символьные и байтовые границы, одновременно предоставленные источником, проверяются отдельно и сохраняются без преобразования или подстановки. Прежний JSON v1 читается при совпадении текущих исходника, спецификации и прав. Хранение всех кандидатов не доказывает полноту смысла: бизнес-семантика остаётся PARTIAL, охват всех бизнес-правил — UNKNOWN.

До использования фильтров и итогов каждый некэшированный сегмент сканируется: индексные id, kind, domain и имя с нормализацией регистра сверяются с каноническим содержимым и ID понятия. Возвращаемые строки проверяются повторно. Внутрипроцессный LRU хранит не более 64 успешных результатов метаданных с ключом из точных путей, полной стабильной идентичности файла, полного SHA, схемы и спецификации производителя. Значения записей не кэшируются. Копирование, замена, изменение хеша или спецификации и вытеснение требуют нового сканирования. Неуспешный читатель не фиксирует ожидающий кэш. Целостность и полнота бизнес-смысла оцениваются отдельно.

## Общий формат передачи исходных записей

Загружаемый исходный JSON сохраняет прежние сериализованные байты. Отдельный JavaScript-файл может кодировать повторяющиеся ключи и строки детерминированным словарём и общим декодером с ограничениями; восстановленные значения совпадают с прежним JSON.parse. Страницы, для которых словарный файл не меньше прежнего, и страницы с допустимыми целыми JSON, округляемыми в неконечные числа JavaScript, используют прежний формат. Сохраняются ограничения точности и диапазона браузера: числа JavaScript не превращаются в точную десятичную арифметику. Для исходного представления чисел доступен исходный JSON. Словарный декодер проверяет разрешённые теги, ссылки, повторяющиеся ключи, количество записей, глубину и байтовые пределы. Сохраняются автономная навигация, исходные загрузки и прежний охват 3D-страницы на пяти языках; fetch и HTTP-сервер не требуются. Проверка транспорта отделена от проверки реального браузера, доступности, производительности и смысла политики.

Последующие контрольные точки и финальная проверка перед публикацией снова читают политику; проверки безопасности файлов, конфиденциальности и снимков сохраняются.

Ответы с правом чтения доказательств и канонические экспорты сохраняют эти данные; сокращённый ответ нельзя повторно использовать как манифест проверки. Функции без ограничений по датам доступны для вычисления; при наличии таких ограничений и отсутствии явного соответствия часов результат остаётся UNKNOWN. Время хоста и произвольное усечение временной метки не используются.

### Точные размерности и вклад политик

Явные контракты количества и денег сохраняют исходный тип `int`. Передаваемые значения остаются строками; для `int` допустима только точная целочисленная запись. Дроби, запись вида `2.0`, значения float, переполнение и несогласованная точность или масштаб остаются неподдерживаемыми без округления. Денежное значение может одновременно сохранять явно проверенные единицу и валюту. Единица является объявленной размерностью: ценовые соглашения и конвертация валют не выводятся. Существующие объявления должны точно совпадать.

`selectedPolicyIds` сохраняет полный список зависимостей. `activeMemberPolicyIds` содержит применимые непосредственные элементы, а `selectedMemberPolicyIds` — элементы, вносящие вклад после выбора приоритета или агрегации. `contributingPolicyIds` и `contributingSourceRuleIds` указывают конечные политики и точные исходные правила. При равных минимуме или максимуме сохраняются все участники; вложенные выборы и лучшие конечные контексты сохраняют собственное происхождение. Для неизвестного или конфликтного выбора списки вклада равны null: победитель не угадывается. Исходные знаменатели элементов и контекстов, а также `globalOptimum=UNKNOWN` сохраняются.

Пропуски из-за бюджета проверки одинаково учитываются в сводке охвата и исходной ведомости обработки; необработанные входы остаются в знаменателе.

Для хеширования ссылок на исходные данные действует отдельный предел глубины JSON 128; встроенный бизнес-JSON сохраняет предел 32. Оба пути сохраняют ограничения в 2 000 000 узлов, 32 MiB кодированных данных, длину строк и ключей и требование конечных чисел. Глубокие исходные структуры связываются точными хешами, не копируются в бизнес-атрибуты и не считаются утверждённым смыслом. Входы сверх пределов остаются неподдерживаемыми в исходном знаменателе. Ранее принятые канонические хеши не меняются.

Потоковый экспорт проверяет каждую полную логическую запись на приватные значения и сохраняет запечатанные байты и хеш. Актуальное состояние проверяется в начале, в конце и между ограниченными пакетами: не более 128 записей или 64 KiB обычного вывода, с кооперативной проверкой истечения 50 мс после каждой записи. Более крупная запись не делится и обрабатывается отдельно, максимум 4 MiB. Отмена или отзыв доступа внутри пакета могут обнаруживаться позднее, чем при проверке каждой записи; 50 мс не являются жёстким сроком для блокирующего ввода-вывода или проверки приватности. Решения о доступе не кешируются; итоговые проверки прав, профиля, снимка и условия атомарной публикации сохраняются. Разделённый экспорт явно сообщает этап подготовки исходного RDF.

## Ограниченная поддержка generic instanceof

Адаптер возможностей Java сохраняет проверяемое выражение, квалифицированные и вложенные сегменты типа, размерности ссылочного массива, имя переменной шаблона, отрицание и контекст ветвей для поддерживаемых форм с неограниченными wildcard, например `Map<?,?>` и `List<?>`. Расширенный узел имеет `op: type_reference` и `syntaxVersion: java.instanceof.type.v1`. Это только синтаксис: `partial` и `instanceof_runtime_unresolved`; фактическое совпадение типа, корректность компиляции и версия Java приложения остаются `UNKNOWN`. Тип получателя переменной шаблона, значения полей, выполнение и утверждённый бизнес-смысл не выводятся. Java SE 21 служит справочником синтаксиса, а не доказательством настройки компилятора приложения.

Лимит выражения остаётся 512 токенов и 32 рекурсивных входа парсера, а не 32 ребра глубины итогового левоассоциативного дерева. Для расширенных типов допускается по 32 квалифицированных сегмента, суммарных wildcard-позиции и размерности массива; общий читатель типа и консервативный резервный проход потребляют не более 512 токенов каждый. Обычные plain квалифицированные типы сохраняют прежние ограничения выражений. Ограниченные, конкретные и вложенные аргументы типа, аннотации, record-шаблоны, некорректный синтаксис и превышение лимитов остаются неподдерживаемыми/UNKNOWN с исходными позициями и причинами.

Возможные имена шаблонов консервативно блокируют конфликтующие внешние и платформенные привязки внутри содержащего callable; при неизвестном владельце — только внутри локального блока или выражения. Исчерпание прохода и неизвестный владелец отмечаются локально, не блокируя другие методы и файлы. Исходные ID и CALLS отделены от этой синтаксической возможности. Сырые JSON/MCP/HTML и SQLite исходного пакета сохраняют синтаксис; проекции графа/RDF не доказывают весь его смысл. Потребитель, не понимающий обязательный узел или версию, должен сохранить UNKNOWN либо отклонить интерпретацию, не удаляя тип и имя переменной. Независимая проверка составителя политики и работа нативного браузера — отдельные этапы. Правила основаны на синтаксисе языка и происхождении данных, без условий по файлам, методам или бизнес-словам конкретного приложения.

Вложенная lambda имеет собственную границу callable: внутренний шаблон не блокирует независимый внешний вызов. Операнды API проверяются в фактической лексической позиции; сводка ссылок только по имени остаётся UNKNOWN, если появления относятся к разным областям.


### Границы синтаксиса присваивания и объявлений record

Семантические фрагменты Java сохраняют исходный оператор присваивания, включая составные арифметические, побитовые и сдвиговые операции. Для поддерживаемой цели в ограниченном подмножестве может быть добавлен условный контракт чтения, изменения и записи. Неподдерживаемые цели сохраняют расположение, причину и статус неполноты. Этот контракт не выполняет выражение и не устанавливает значение цели, побочные эффекты или фактическое поведение при выполнении.

Инвентаризация членов record различает компактные конструкторы и поддерживаемые заголовки явных конструкторов. Ограниченно поддерживаемые заголовки перегрузок могут сосуществовать с компактным конструктором, не скрывая объявленные компоненты record. Распознавание заголовка не доказывает корректность компиляции, поведение тела, делегирование или соответствие параметров полям. Неоднозначные сигнатуры, неподдерживаемый синтаксис и конфликтующие объявления сохраняют UNKNOWN. Сериализованный вид области `record_explicit` является синтаксическими метаданными. Потребитель, не распознающий его, должен сохранить исходную запись с явным статусом отсутствия поддержки. Статические объявления и доказательства типа получателя отделены от выбора вызова во время выполнения.

## Явное сравнение переданных числовых наблюдений

`compare_policy_cases` по умолчанию использует `comparison_mode=source_contexts`, даже когда параметры исходной функции названы `id` или `value`. Явный `supplied_values` требует `knowledge_view=business`, существующие конкретные source/business pins и право чтения политики. Исходное правило и необязательная композиция политик не вызываются: `sourceEvaluation` равен null, `sourceRuleEvaluated` — false. Существующие проверки отзыва, конфликтов и одобрения сохраняются. Одобрение бизнес-записи не подтверждает истинность и допустимость переданных значений; выполнение и допустимость остаются UNKNOWN.

Каждый случай содержит ровно `id` и `value`. ID — уникальная непустая строка без управляющих символов длиной до128 знаков. Значения — целые числа либо существующие типизированные объекты `integer`, `decimal`, `quantity`, `money`. Модуль целого ограничен10**100; десятичная строка использует прежнюю обычную запись без экспоненты длиной до128 знаков. Указанная точность проверяется, отсутствующая не выдумывается. Целые и десятичные scalar сравнимы между собой, для количества нужна точно одинаковая единица, для денег — одинаковый кортеж валюты и необязательной единицы. При смешении семейств, единиц или валют все иначе корректные числовые элементы несравнимы; произвольная опорная группа или конвертация не выбирается. Сервер точно сравнивает переданные значения, но не восстанавливает точность, уже утраченную клиентом.

`suppliedComparison` сохраняет исходные `inputIndex`, `/cases/<index>`, допустимый ID, canonical digest входа, решение и причину. Пропущенные, неподдерживаемые, неверные и дублированные элементы остаются в исходном знаменателе. minimum, maximum и best возвращают все равные ссылки index/ID в исходном порядке; значения остаются в entries. COMPLETE означает принятие всех выбранных значений только для этого локального сравнения. Неразрешённые или отклонённые элементы дают PARTIAL; поддержанное подмножество не является полной ранжировкой. Глобальный оптимум и полнота всей политики не доказываются.

Весь исходный cases проверяется privacy-guard до hashing кандидатов/запроса и частичного вывода; отказ отклоняет запрос целиком. Лимиты —100 случаев и64KiB canonical cases плюс прежние protocol-ограничения всего запроса. Внутреннее превышение возвращает BLOCKED с необработанным frontier; некорректный или чрезмерный protocol-запрос отклоняется до вызова и не доказывает обработку отдельных элементов. Идентичность запроса связана с исходными случаями, целью, режимом, текущими pins и разрешённой проекцией политики. Читатель только политики не получает дополнительные скрытые digest доказательств отдельных записей.


## Отображение незавершённой обработки

Для распознанных типизированных функций политики сохраняются результат обработки (извлечено, не поддерживается или не проанализировано), позиция в исходном коде и фиксированная причина. Это метаданные покрытия, а не подтверждение смысла политики или выполнения. Записи используют существующий лимит деклараций. Даже при нулевом остатке отдельная сводка сохраняет числа распознанных, записанных и пропущенных результатов. Знаменатель относится только к распознанным кандидатам; общее число функций исходного кода и полнота бизнес-смысла остаются UNKNOWN.

Статус бизнес-представления MCP отделяет последнюю зарегистрированную неопубликованную сборку от опубликованного снимка. При праве `read_evidence` и совпадении исходного снимка он сообщает обработанные и пропущенные записи относительно исходного числа выбранных записей, а также факт публикации. Конкретный виновный вход и история всех попыток не предполагаются. Отсутствующая, неверная, изменившаяся при чтении запись и несовпадение источника обозначаются явно. Читатель только политик получает WITHHELD без проверки записи. Хеши, количества и идентификаторы другого снимка не раскрываются; бизнес-снимок старого источника не считается текущим для нового.


## Частично известные числовые свойства

Числовое свойство сохраняет известную точность или число десятичных знаков, оставляя другое значение UNKNOWN. Округление, единицы и валюта остаются отдельными фактами. Неизвестное не заполняется из настроек вычислителя или вида числа. Если оба значения известны, число десятичных знаков не должно превышать точность (scale <= precision). Проверка конкретных чисел не меняется. Десятичные вычисления требуют полного контракта точности, числа знаков и округления. Одобрение и передача MCP не доказывают выполнение или полноту бизнес-смысла.

### Ограниченные контракты порядка сравнения и статуса ответа

`Comparator.comparing`, `comparingInt`, `comparingLong`, `comparingDouble`, соответствующие варианты `thenComparing*` с одной функцией извлечения ключа и `reversed()` используют существующий путь статических API-контрактов. Callback ключа требует единственного доступного, непосредственно объявленного исходного метода без static, обобщений, varargs и параметров либо уже поддерживаемого аксессора record. Поддерживаются несвязанная ссылка `Type::key` и прямая lambda-формула с доказанным входным типом. Статические и связанные ссылки, неоднозначные перегрузки, унаследованные getter, блочные lambda, неизвестные входные типы и другие перегрузки Comparator сохраняют UNKNOWN.

Необязательные доказательства revision-1 `Method.callbackDeclaration` и `Type.callbackMemberInventory` связывают разобранное объявление с исходным владельцем, digest и диапазонами. До выбора callback существующий полный список непосредственных членов должен согласоваться со всеми выданными записями методов. Отсутствующие, дублированные, изменённые или недоступные доказательства отзывают зависимый смысл. Диапазоны callback и параметров используют позиции символов декодированной Python `str`, от нуля и без конечной позиции; это не байты UTF-8 и не единицы Java UTF-16.

Варианты с примитивными ключами требуют точно `int`, `long` или `double`. Естественный порядок допускает только точные документированные номинальные типы `String`, `BigDecimal`, `Instant`, `Integer`, `Long` и `Double`; переопределения в исходном коде, подтипы и недоказанные обобщённые отношения Comparable не подходят. Равенство для порядка означает `compareTo == 0`, а не `equals`: сравнение BigDecimal игнорирует scale, а Double сохраняет документированный порядок NaN и нулей со знаком. Приоритет ключей сохраняется. `reversed()` меняет направление доказанных ключей своего получателя; добавленный позже ключ для равных значений начинается в прямом направлении. Неизвестное звено прерывает композицию; инициализаторы переменных и полей не подставляются.

Spring `ResponseEntity.badRequest()` и `notFound()` сохраняют публичные константы спецификации 400 и 404. `status(int)` и `status(HttpStatusCode)` сохраняют указатель на аргумент со значением UNKNOWN. Ограниченный целочисленный AST, допущенный существующей проверкой приватности, выбирает `status(int)` только при точном совпадении исходного доказательства `java_literal_type` int. Десятичная строка wire остаётся неизменной: значение не копируется в metadata статуса, исходные токены не перечитываются. Грамматика quoted-literal review не меняется и для этого существующего числового пути не требуется. Маскированные, непрозрачные, слишком большие, выходящие за диапазон, long, floating, поддельные или отозванные доказательства остаются UNKNOWN. Непосредственно связанный поддерживаемый `build()` сохраняет доказанное отношение статуса и контракт отсутствия тела при успешном создании. Отдельный builder не получает статус. Фактический получатель `BodyBuilder` и объявляющий член `HeadersBuilder` остаются различными и проверяются через конечный документированный bridge получателя.

Java SE 21 и Spring Framework 6.2.12 являются отдельными нормативными ориентирами. Фактические версии, компиляция, выполнение callback, выбор вызова, сортировка и доставка HTTP остаются UNKNOWN. Пределы: 16 ключей порядка, 16 записей доказательств callback на фрагмент, 64 метода-кандидата на callback и 32 KiB новых метаданных, с сохранением более строгих существующих бюджетов. Неподдерживаемые и пропущенные входы остаются в исходном знаменателе. ID, диапазоны, CALLS и канонические байты прежних API-записей сохраняются; добавление необязательных доказательств и контрактов меняет digest записей и sourceSpec. Прежние доказательства создания enum и record остаются независимыми.

Исходные JSON/MCP, детали HTML-записи и SQLite исходного пакета сохраняют необязательные доказательства. Граф/RDF сохраняют объявленные проекции без создания рёбер порядка, статуса или CALLS. Читаемость исходных данных не доказывает семантическую совместимость: интерпретация требует распознавания возможностей revision-1 для callback, порядка, статуса ответа и bridge получателя, а также строгой проверки catalog и исходных доказательств. Диагностика статуса использует общую возможность статуса ответа. Старые или неизвестные потребители должны явно сохранять UNKNOWN, отклонять интерпретацию либо показывать помеченные исходные данные. Отказ старого потребителя принять bridge не является успешной совместимостью интерпретации. Новый UI, движок или схема базы данных не подразумеваются.

`capability`: `java-source-key-callback-1`, `java-comparator-ordering-1`, `spring-response-status-1`, `spring-response-receiver-bridge-1`.

Явные аргументы типов метода должны точно совпадать с уже доказанными типами: primitive factory требует `<T>`, естественный `comparing` — `<T,U>`, а естественный `thenComparing` — `<U>`. T обозначает входной тип callback, U — конечный Comparable тип ключа. Неверное число, неизвестные или несовпадающие аргументы оставляют внешний контракт UNKNOWN, сохраняя независимо доказанный получатель. Явные аргументы primitive вторичного ключа и `reversed()` не поддерживаются в данном ограниченном подмножестве; это не утверждение о незаконности Java. Явный тип параметра lambda использует пространство имён типов, поэтому одноимённый параметр значения, локальная переменная или поле сами по себе его не скрывают. `Type::method` сохраняет отказ при неоднозначности имени значения; действительное затенение типа остаётся неподдерживаемым. Производитель и валидатор доставленных записей применяют одинаковое различие без нового generic solver.

Для явных T/U дополнительно требуется необязательный Type `callbackTypeNamespace` revision 1: выбранные прямые вложенные типы, локальные/нечленские типы и типы верхнего уровня того же пакета связываются с доставленными Type ID, путями, digest исходника и символьным `/sourceRange`. Статус `complete` требует точных целых счётчиков, не boolean (`detectedDeclarations = len(declarations) + omittedDeclarations`), отсутствия пропусков и существующей полной проверки членов. Предел списка 64, прежние 62 ID зависимостей, 16 внешних областей и 32 KiB контракта сохраняются. Недостающие, изменённые, повторные, неполные, удалённые или превышающие бюджет доказательства оставляют UNKNOWN только для соответствующего явного контракта. Область действия локального типа и наследование вызывающего/внешнего типа этим конечным расширением не разрешаются и остаются UNKNOWN. Одноимённые значения не блокируют имя в позиции типа. Неявные контракты и независимые получатели сохраняются. Type payload и digest доказательств меняются, но source ID, символьные диапазоны, CALLS и прежние catalog entry bytes неизменны. Существующие MCP/SQLite/HTML reader сохраняют поле; raw читаемость старого потребителя не означает проверенную семантическую совместимость.

Проверка списка типов двунаправленная: каждая запись связывается с source Type, а независимо известные callback owner, вызывающий, внешние и ссылочные Type обязаны присутствовать в соответствующем complete списке. Несколько ролей доказательства одного Type не разрешают удалить его из списка, даже если ID зависимости остаётся в другом месте. `known_types` принимает только реальные доставленные Type record, совпадающие с lookup; потребитель сначала отбирает непосредственные lexical child и типы верхнего уровня того же пакета, сохраняя предел 64. Равенство счётчиков, объединение ID и собственный digest не доказывают отсутствие. Ненаблюдаемые и превышающие бюджет данные оставляют явный смысл UNKNOWN. Внутренняя согласованность не заменяет доверенное source/snapshot provenance при согласованной подделке всего снимка; raw сохранение отделено от семантического признания.
