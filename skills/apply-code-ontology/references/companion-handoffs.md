# Optional companion handoffs

Use only the other product's skill and execution route currently available in this conversation. A local installation, development checkout, exposed skill, or coordinator descriptor is not proof of a successful call. If no supported route is runnable, mark that product pending and continue Code independently. Do not install, import, reconfigure or duplicate another product to satisfy the requested combination.

An explicit product request takes precedence: applying Code alone does not request Context storage or Contracts validation. For generic setup, use the available selected products where the current task has appropriate inputs; state any missing input without inventing one. Reuse a working setup and an equivalent verified record or artifact instead of creating duplicates.

## Context Ontology Companion

Follow the available Context skill to inspect its actual state and storage scope. When the requested application includes Context, select only the minimum user-explicit, confirmed goal, constraint or decision needed to continue the present task. Keep scope and provenance. Do not promote assistant inference, a proposed option, source comments, or a historical approval into a confirmed decision or current authority.

Use the product's real storage operation only within the requested scope, then retrieve the resulting record with its real identifier and check the stored content. A prepared payload or reported record ID without readback is incomplete. If there is no confirmed information or no authorized storage scope, report that step as pending while continuing independent work. Do not fill a record merely to get a success label.

For source evidence, read the sibling [Code reference contract](../../manage-code-ontology/references/code-reference.md). A narrow `{id, origin, locator}` projection may be compatible with Context; it is not the entire Code evidence artifact. Retain the immutable original locally and ensure its locator resolves to the same digest and evidence. Record only what the actual Context route supports. Missing originals, lossy projections and unsupported native imports remain explicit. Do not store or upload the full graph, source code, private absolute paths or unrequested evidence.

## Ontology Companion Contracts

Follow the available Contracts skill and validate the actual JSON artifact exchanged in this task against the actual supported contract/profile version. A fabricated example, schema inspection, native Code export or coordinator plan is not a successful Contracts validation. Use the bounded selected references needed for the task and verify the actual validation result.

Preserve `loss`, `unsupported`, `not_checked`, source/snapshot bindings and any other compatibility findings. In particular, a local Git HEAD observation does not establish source-to-commit binding. If the available exporter cannot construct a supported Contracts artifact, keep the unsupported result; do not invent missing bindings or drop fields to claim compatibility. Code's native reference format remains usable independently.

Validation establishes only the claims that the actual validator checks. It does not prove the source is true, the runtime followed a path, Context stored a record, the user approved an action, or the task is complete. Hand off to Context only if requested, using its own supported operation and readback.

## Completion evidence

- Code: real status and task-relevant query/impact, matching snapshot and stated support/freshness.
- Context: actual scoped write or reuse, followed by retrieval of the confirmed record.
- Contracts: actual exchanged JSON and actual validator output, with compatibility losses and unchecked claims retained.

Report each result separately. A completed Code step can coexist with a pending Context or unsupported Contracts step; do not label the combined workflow complete in that case.
