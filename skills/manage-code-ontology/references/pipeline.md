## Current public source-pipeline human view

`analyze`, `refresh` and ordinary `pipeline-html` publicly default to the bounded human presentation: area → major structural module → core overview, default depth 2 and maximum 3. Load at most 32 nodes and 64 aggregate edges per view; five UI languages share local script chunks, and search covers only the current summary page. Whole mode returns to the whole-scope aggregate root; camera reset does not change scope. Source policy cards are opaque evidence tiles with meaning UNKNOWN, not complete human narratives of conditions, calculations or exceptions. Exact/deep data remains in MCP. `--presentation records`, legacy workbenches and explicit partitioned record exports remain separate supported routes; this does not make every business export a human summary. HTML abstraction never removes policy meaning required in an AI answer or policy document. Privacy, ACL, current source bindings and invalidation remain mandatory.

Before writing policy prose, use the [fact worksheet and quality workflow](../../../docs/QUALITY_0_9_3.md). Worksheet completion is not policy-prose coverage; retain the separate coverage denominators.

## Start and refresh

Use Python 3.9 or newer and the trusted installed bundle. `COMPANION` below means its `skills/manage-code-ontology/scripts/companion.py`; Windows can use `py -3`. Choose a new workspace outside the authorized source. Set `CODE_ONTOLOGY_PRIVACY_FILE` to your private identity-deny profile outside source and output roots before HTML or portable export. The profile is never copied into knowledge artifacts. Missing protection is an error for export.

```sh
python3 "$COMPANION" analyze --repo /path/to/source --workspace /path/to/knowledge --authorized --language en
python3 "$COMPANION" refresh --workspace /path/to/knowledge --language en
python3 "$COMPANION" pipeline-status --workspace /path/to/knowledge
```

For a large source collection, add `--capacity large` to `analyze`: ceilings become 250,000 files, 4 GiB input, 5 million records, 8 GiB snapshot output and 7,200 seconds. Defaults remain 25,000 files and 512 MiB input. This is explicit budget selection, not proof that every workload fits. HTML and portable exports keep their separate 1 GiB output limit; use `--no-html` when only sealed knowledge is needed. The per-file AST limit is 20,000 nodes by default and 200,000 with `--capacity large`; source bytes, rule IR and depth limits still apply.

The first command builds sealed knowledge, creates the private owner access policy, registers the workspace for MCP and generates five-language HTML. `--source-root` may be repeated. `--no-html` performs analysis only. `--label` accepts a safe project alias. Refresh keeps old snapshots and reuses unchanged file facts while rebuilding cross-file resolution. Cancellation or failure preserves the prior published snapshot; `pipeline-recover --workspace /path/to/knowledge` resumes or completes a verified interrupted local run. A new generation is not published if source or catalog identity changed during the run.

New pipeline workspaces use `pipeline.json` and immutable partitioned SQLite snapshots. Existing `init`/`sync` workspaces and large-project catalogs remain compatible; they are not silently converted or merged. Pipeline status verifies saved artifacts without opening source files and reports `freshness=not_checked`. Refresh is the operation that verifies the source again.

## What is analyzed

| Family | Implemented boundary |
| --- | --- |
| Python | AST-based declarations, imports and supported static relationships; restricted typed pure-function policy extraction. Dynamic execution remains unknown. |
| Java, JavaScript/TypeScript, SQL, Vue, XML/MyBatis | Conservative syntax/declaration/import and selected framework patterns. These are not full compiler, SQL-dialect or whole-program proofs. Dynamic SQL and reflection remain unresolved. |
| Kotlin, C#, Go, Rust, C/C++, PHP | Bounded declaration/import recognition, with explicit partial coverage and unresolved semantics. |
| Swift, Dart, Ruby, Scala | Bounded declaration/import recognition; complete language semantics and policy extraction are not implied. |
| Bash/POSIX shell, PowerShell | Bash functions, source references, command/pipeline and control-flow boundaries; PowerShell declarations/imports. No script execution, expansion or secret argument collection. Ambiguous quote/heredoc regions are withheld. |
| LangChain/LangGraph, Kafka, Redis | Selected declared agent/tool/graph or messaging/cache relationships. Environment-unknown resources stay separate; raw prompts, keys, values, credentials and runtime success are not collected. |

Each file exposes language, adapter/rule version, source digest, evidence span, analysis level and limitations. An unsupported construct is never silently promoted to resolved knowledge. The broader framework backlog in the archived design remains a roadmap, not a claim that every SDK or version is supported.

The engine uses bounded file batches, one writer and disk partitions. `workers=1` is the implemented execution profile. Explicit higher file/byte/record budgets are available through the engine API; larger limits are safety ceilings, not demonstrated capacity. Graph queries are paged. Complete policy evaluation has a separate rule budget and fails instead of calculating with a silently truncated ruleset.

## Policy knowledge and AI use

The six domain candidates are `product`, `order`, `display`, `claim`, `settlement` and `delivery`. Classification from identifiers is a candidate, not business ownership approval. Policies retain conditions, typed inputs, program order, source assertions and unsupported boundaries. The supported Python fragment includes typed booleans/integers/Decimal, assignment, early returns, boolean conditions and explicitly supported arithmetic/rounding. Unsupported calls, exceptions and loops do not become verified policies. Java and TypeScript support pure, explicitly typed boolean condition functions; numeric, framework-driven, and dynamically dispatched policies remain unsupported. See the generated coverage for the exact supported fragment.

The four policy MCP tools are `list_domain_policies`, `query_policy_rules`, `compare_policy_cases` and `explain_policy_result`. Four additional tools are `ontology_pipeline_status`, `ontology_pipeline_search`, `ontology_pipeline_modules` and `ontology_pipeline_coverage`. The full package has 20 read-only tools, including the 12 existing tools. Skills-only includes setup guidance and the analyzer, not the MCP server.

1. Use `ontology_list_workspaces` and choose a `pipeline` workspace.
2. Obtain a concrete snapshot ID from `ontology_pipeline_status`.
3. Pin that ID in all related reads. `current` or arbitrary filesystem paths are not accepted as query pins.
4. Read a rule, then supply explicit typed context to explain or compare. Amounts use decimal strings where the rule declares Decimal.

`verified_implemented` is the default authority view. `AI-proposed` is excluded from calculation. `approved_business` requires independent explicit approval metadata and is never inferred from extraction success. Model identity and semantic verification are distinct. The default engine uses no model: `modelNotUsed` / `N/A`. No cloud API, model installation, automatic model switch or source transmission is added.

Policy questions use the sealed policy snapshot; they do not reread code or query live databases, brokers or caches. Missing eligibility, usage counts, configuration or time inputs remain `needs_context` or `UNKNOWN`. A maximum over supplied samples is `best_found`. `proven_maximum`/`proven_minimum` requires complete supported scope, exact snapshot/ruleset pins and exhaustive independently known finite inputs; its stated scope never means every policy in an organization. Source-extracted behavior is not business approval or proof of live eligibility.

Local MCP responses may be forwarded by the host to a remote model. Authorizing local source analysis does not authorize that transmission. Select and approve the evidence to send separately.

## Knowledge access

`access.json` is a private local policy. Initialization grants only the operator-bound pseudonymous owner. The trusted launch environment selects `CODE_ONTOLOGY_PRINCIPAL`; its default is `local-owner`. A tool argument cannot select a principal or role. Run separately configured MCP processes for different trusted principal bindings. This is a local process/OS account boundary, not a remote login service or identity provider.

Permissions are `read_structure`, `read_policy`, `read_evidence`, `export_html`, `export_bundle` and `manage_access`, optionally pinned to specific snapshot IDs. Unknown principals, missing or unsafe ACLs, unsupported actions and snapshot mismatches fail closed. Policy-only query responses keep opaque evidence IDs but withhold source locator details; the separate evidence permission is required for those details. Legacy workspaces remain local-owner-only. Permission changes are reread on subsequent requests, not cached as permanent grants.

An explicitly invoked local operator command replaces a principal's grant; it is absent from MCP:

```sh
python3 "$COMPANION" pipeline-access --workspace /path/to/knowledge --principal policy-reader --action read_policy --snapshot SNAPSHOT_ID
```

Omitting `--action` revokes that alias's operations. At least one unrestricted access administrator must remain. Use aliases, never personal names or emails. Domain inference is not an authorization label: this release does not claim trustworthy row-level domain isolation. Use distinct authorized workspaces for separate confidentiality boundaries.

HTML export requires `export_html` plus all three read permissions. A portable export requires `export_bundle` plus all three read permissions. Generated HTML is an offline copy: later ACL changes cannot revoke copies already made. Protect export files and their recipients separately. POSIX ownership/modes and available Windows handle ACL checks fail closed; native Windows execution requires independent verification.

## Human HTML, lineage and interchange

**Legacy / explicit records workbench scope** — The generated HTML has Korean, English, Japanese, Simplified Chinese and Russian versions. Catalogs, modules, records and policy decisions use bounded pages and exact evidence anchors. Search and 3D cover the displayed page, with complete records reachable through pagination. Existing 3D focus/full controls, reduced motion, text navigation and mobile touch targets remain. Relative links work offline without `fetch` or a required HTTP server. A static page does not imply current source or runtime behavior.

RDF 1.1 Turtle represents assertions and provenance using [PROV-O](https://www.w3.org/TR/prov-o/). [SHACL](https://www.w3.org/TR/shacl/) checks required shape properties; it does not certify truth. Snapshot manifests bind artifact checksums, analysis specification, coverage and source verification time. Checksums are integrity evidence, not trusted signatures. Private source manifests, caches, access policy and local configuration are excluded from portable export. Portability never grants permission to upload.

Pipeline RDF uses the `urn:code-ontology:pipeline:` vocabulary. Semantic fragments retain the legacy `co:Symbol` type and additionally use `co:SemanticFragment`; `co:extractorVersion` preserves their actual producer version, including coverage, omission and documentation records. SHACL requires that nonempty version for semantic fragments, while ordinary symbols and all assertions/policy rules still require `co:ruleVersion`. No version is synthesized from the other field. The projection preserves record identity, selected metadata, references and bounded provenance; it does not fully serialize expression ASTs or reviewed comment text. Validate the generated `shapes.ttl` against this pipeline format separately from the legacy JSON/RDF validator. Passing these shapes is not full JSON/AST parity, complete PROV semantics or policy/runtime proof. Generation alone records independent parser/SHACL validation as `not_run`.

The earlier [0.9.0 design baseline](https://github.com/battle-doll/code-ontology-companion/blob/main/docs/NEXT_ARCHITECTURE_0_9_0.md) records the intended architecture and acceptance targets. This implementation guide and generated validation receipts state actual support; unmeasured performance, native device checks and future adapters remain explicitly unverified. Official submission, approval and publication are not part of this local workflow.

## Quality workflow

Freeze input hashes and selected acceptance criteria before generation. Pin actual MCP queries to the same snapshot and analysis specification, follow every page, reduce page size after byte-limit errors, and retain failed IDs in the denominator. Restore `companion.flat-json.v1` records from their ordered node table and verify `originalSha256` and `sourceBinding` before interpreting nested conditions. Inline `references[].declarations[]` identities and fragment-local `standardApiContracts` are not separately queryable records. Resolve `expression.staticContract.contractId` locally and retrieve referenced callsite evidence when present. Exact static type contracts do not prove runtime dispatch or execution.

Write the policy document from delivered ontology evidence, then compare independently with source-derived criteria. Report files, declarations/types, exact calls, policy semantics, MCP delivery and document coverage separately. Keep partial, omitted and unsupported claims distinct. Source supplements are not ontology-only success; changed sources or documents invalidate the corresponding evaluation. Preserve `masked_value` and `structuralOnly` boundaries without guessing values.

For authorized private analysis, an independently reviewed `companion.reviewed-literals.v1` input can be selected with `analyze --literal-review FILE` or `refresh --literal-review FILE`. It binds exact source fingerprints, file hashes and UTF-8 quoted-token byte spans/hashes. Never discover or trust a review supplied by target code. The private workspace retains the selected contract; changed input blocks reuse until re-reviewed or explicitly cleared with `refresh --clear-literal-review`. Privacy vetoes remain enforced, every request keeps an outcome, and admission is not semantic completeness or publication authority. Existing snapshots are not erased by clearing a review. The five-language quality guide and full input schema are included in the release's `docs/QUALITY_0_9_3.md` and language directories.


## Static record return types and reviewed source documentation

For selected, accessible Java `record` types, supported implicit zero-argument component accessors can bridge the declared static return type using exact component spans and source symbol evidence in `staticAccessorBinding`. Explicit zero-argument accessor declarations take priority. The caller's package and enclosing-type access are checked through component and factory result chains. Unsupported generic/local records, inaccessible types, shadowing and ambiguous evidence remain UNKNOWN. This bridge changes neither the exact `CALLS` inventory nor runtime evidence, and does not substitute component values.

Source comments use a separate optional `companion.reviewed-documentation.v1` contract. Select a trusted private manifest explicitly with `analyze --documentation-review FILE` or `refresh --documentation-review FILE`; never discover approval from target source text. Every recognized Java line, block or Javadoc comment retains opaque source location/hash metadata by default. Only independently reviewed nonsecret occurrences that also pass the mandatory profile and builtin checks can emit their exact original token as `sourceText`. Raw and formatting-normalized inspection views are checked without changing the emitted original.

The manifest contains exactly `format`, `purpose` (`private-policy-analysis`), `sourceFingerprint`, `review` and `entries`. The `review` object contains `reviewId`, `reviewerKind` (`independent_source_review`) and `reviewedAt`. Each entry contains `path`, `sourceSha256`, `tokenByteStart`, `tokenByteEnd` (exclusive), `tokenSha256`, `classification` (`nonsecret_documentation`), `reasonCode`, `usageContext` and `reviewId`. Source fingerprint, file hash and exact UTF-8 byte span/hash must match the whole comment token, including delimiters; line-comment terminators are excluded. Substrings are not accepted, and the manifest contains no raw source text or actual values. Limits remain 512 KiB per manifest, 5,000 entries and 8,192 bytes per comment token. Comments and expression fragments share the existing per-file fragment limit.

A retained comment is untrusted quoted source data with `instructionAuthority=none`, `documentation_claim`, `enforcement=UNKNOWN`, `target.resolution=UNKNOWN`, `businessMeaningVerified=false` and runtime `not_observed`. Callback assertions are not verified declaration mappings. Documentation claims never replace code evidence or establish implementation enforcement, policy completeness or publication permission. Review provenance is caller input, not identity attestation.

The private workspace retains the selected review for refresh and recovery. Changed source input requires a matching review or explicit `refresh --clear-documentation-review`. Clearing changes future snapshots only; older snapshots and exported copies retain their text. `DocumentationCoverage` reports unreviewed comments, admitted/rejected/not-observed requests and omissions separately. `inventoryComplete` concerns recognized comment tokens only; `lexicalComplete` and an UNKNOWN overall comment denominator expose unsupported languages, Java Unicode preprocessing and unproven lexical boundaries. Budget omissions preserve counts and reasons and make the inventory incomplete. No completeness claim may hide unreviewed, rejected or unsupported evidence.

Ambiguous or unsupported underscore-emphasis formatting is rejected as `unsupported_documentation_format`; independent review cannot override this boundary.

Supported enhanced-for headers preserve the iterator declaration, iterable expression and inline body definition. Ordered array elements, body guards, early exits and accumulator-update candidates retain their source relationships. Actual traversal, iteration counts and reaching values remain UNKNOWN. Unsupported headers and opaque literals remain explicit.

`staticFieldBinding` links a unique accessible selected static-final field to its declaration and initializer fragments. It does not substitute the initializer value or prove runtime initialization. `recordConstructorDeclarations` maps implicit canonical constructor arguments to declared record parameter positions. Explicit or compact constructors retain candidates and unknown value transfer; no synthetic exact CALLS or runtime field values are asserted.

Documented standard overloads include decimal remainder and nanosecond subtraction. Remainder can be negative and is not nonnegative modulo; a MathContext constrains its implicit integral quotient, while the remainder itself is exact. Time contracts retain units and exception conditions. Numeric types alone do not establish business units.

Resolve `source-body:`, `source-binding:` and `source-record-constructor:` identities in their containing fragments before requesting separate records. Loop references identify the defining fragment and body location; constructor references identify the local declaration catalog. Source field references require the actual declaration and initializer fragments. `sourceRange.charStart/charEnd` uses zero-based Unicode code points with an exclusive end; reviewed literal/comment manifests instead use UTF-8 byte offsets. Check the snapshot, source digest and definition closure for both.

After final review, missing, mismatched or revoked definitions withdraw dependent type, accessor, constructor and API proofs. Raw syntax and independent sibling evidence remain available. Final snapshots reject pending dependency closure; UNKNOWN is not promoted to a supported claim.

Record symbols carry an independent source declaration catalog: `recordComponents` entries contain `index`, `name`, sanitized `declaredType`, `type`/`typeResolution`, `typeReason`, `declarationStatus` and `sourceRange`. The parent supplies the actual Record ID, qualified name, path and source digest. Parent `sourceRange` covers the declaration; `recordHeaderRange` covers the component-list parentheses. All these ranges use zero-based Unicode code points with exclusive ends. Validate each active component against its actual parent and range containment; an absent constructor call/catalog is not a missing record declaration. `recordComponentCoverage` reports the original detected count, emitted count, omitted count and unsupported emitted entries. Header failure leaves the detected count unknown. The projection emits up to 64 entries; names/types over 1,024 characters are withheld with an explicit text-budget reason. Neither limit truncates shared parser state or raises delivery limits. Incomplete or malformed declarations stay PARTIAL, and unknown type pairs remain null/UNKNOWN. The existing primitive signature convention uses `java.lang.<primitive>` only with `typeResolution=primitive`; only the eight Java primitive names correspond to unprefixed AST primitive types, never wrappers or numeric conversions. Annotation argument values are excluded. This is declaration observation, not a constructor-value transfer, new exact CALLS edge or runtime guarantee.

`staticFieldBinding` and `receiverStaticFieldBinding` are discriminated by `resolution`, not a single static-final schema. For `selected_static_final_field`, validate the actual emitted field declaration and initializer evidence against their IDs, path, source digest and ranges. For `declared_record_component_field_type`, validate the delivered parent Record ID/qualified name/path/digest and the matching declared `recordComponents` name, component range and type pair. Neither an initializer nor a constructor-call catalog is required for this record-field declaration evidence; runtime value remains UNKNOWN. Match `staticFieldBinding` to the value node’s `staticType`, and `receiverStaticFieldBinding` to its `receiverStaticType`, never to a call’s return `staticType`. An unknown discriminator cannot be treated as either known schema. Conflicting explicit imports preserve null/UNKNOWN types with a reason. A void component or nonfinal varargs produces unsupported/PARTIAL declaration metadata with the original observed inventory. These bounded checks are not full compilation or a new runtime/call-resolution proof.

Java block-local `var` declarations may reuse an initializer static type already supported by source-bound expression analysis. `localTypeInference` binds declaration, initializer and lexical scope ranges to the file digest; consumer types refer to this definition through `localTypeBinding`. Links stay compact, and the existing dependency-depth bound remains enforced. Unknown, malformed, self-referential, multi-declarator, redacted or unsupported initializers stay UNKNOWN. Missing or revoked definitions withdraw dependent type/API proofs while preserving syntax and independent siblings. Coverage counts emitted `var` declarations separately; original omissions remain in the fragment inventory. This is bounded static type propagation, not value evaluation, definite-assignment proof, general generic inference or execution evidence. The bounded language reference is [JLS 21 section 14.4](https://docs.oracle.com/javase/specs/jls/se21/html/jls-14.html#jls-14.4). Local definition IDs refer to emitted fragments, not separately invented records.

The local initializer bridge additionally joins token-proven named-type/callable body ranges to the Java index through lexicalCallableOwner. localTypeInference.lexicalOwner retains the callable/type symbol IDs and exact body ranges; finalization validates emitted symbols, source hashes and use ownership. Local/anonymous types and unproven enclosing-field fallback remain UNKNOWN; this change does not implement local-class statement splitting or infer an inherited field by name.

Java type/callable symbols now project exact sourceRange=declarationRange plus bodyRange through one shared range calculation. lexicalOwner carries both declaration and body ranges and actual symbol IDs; controlFlow.owner.id joins the emitted callable symbol instead of a synthetic undeclared callable record. Finalization compares the actual definitions, ID/name/owner/path/hash, complete declaration ranges, body ranges and file bounds. The declarationSpan contract applies to full declarations; span/headerSpan are not treated as full-body spans. Extraction validates against actual in-process projected records; later finalization without an owner-record lookup leaves inferred locals UNKNOWN.

Java inherited-name checks may use the bounded `java-se21-member-inventory-1` catalog for exact platform identities. `javaStaticModel` in the snapshot and analysis specification records the effective Java SE 21 assumption; `actualTargetJdk` remains `UNKNOWN`. `platformTypeContracts` contains deduplicated field/member-type/parent inventories and primary specification links. Compact `platformInheritance` references resolve to `platformInheritanceChecks` in the same fragment (or Record symbol), with selected source declaration IDs, path/digest, header ranges and parent-reference positions. Type symbols expose `sourceRange` and `declarationHeaderRange` as zero-based, end-exclusive character offsets. These are bounded lexical observations and documented platform assumptions, not target-JDK discovery, complete member export, exact CALLS, execution or runtime-value evidence. Unknown parents, ambiguous imports, selected platform impersonations, present hiding members and projection limits retain explicit uncertainty. This model does not infer local `var` types. The platform inventories cover only their stated inheritable field/member-type namespaces and direct parents. Source-parent identity must match the delivered declaration and its extends/implements reference. An unknown transitive edge prevents an absence proof. Limits are 16 visited source/platform scopes, 64 projected source-parent edges per query, and 64 deduplicated checks or 64 KiB of check/catalog metadata per record; exceeding a limit withholds dependent evidence and records the limitation. Existing file, node, depth and output caps are unchanged. Catalog IDs are inline definitions, not sourceEvidenceIds or separately stored records. Late dependency invalidation prunes unused positive lookup and catalog entries; diagnostic UNKNOWN checks are not positive evidence. The `omittedChecks` diagnostic counts omitted lookup attempts, including repeated requests; it is not a count of unique source declarations or policy rules.

Before an inherited-name absence can support a type or API contract, each selected source scope must have a verified inventory for the required namespace. `sourceScopes[].memberInventory` records separate field/member-type status, the count of consumed direct declaration regions (not the field count), and sorted unique `fieldNames`. Bounded complete direct field statements can contain several declarators; generic type commas are distinguished from declarator commas, and every field initializer must be fully consumed by the supported bounded expression grammar without evaluating values. Valid record component headers supply implicit field names, and supported enum constants supply direct field names. Actual hiding fields remain present. Annotated fields/constants, unsupported or unverifiable constructor headers, unsupported or malformed regions, Unicode-escape boundaries and scan limits retain `UNKNOWN` for the affected namespace. This does not extend JavaIndex, exact CALLS, runtime values or whole-policy coverage. The source scan is capped at 1,024 direct declaration regions and 32 nested balanced groups; existing output limits remain unchanged. `transitiveInventoryComplete` refers only to the lookup namespace: an unverified field inventory does not by itself invalidate a separately verified member-type lookup. A source declaration may be accessible while its field inventory remains unknown. Canonical platform entries remain unchanged and are inline model definitions, not source declarations. Supported owner-matching class/enum constructor headers and compact record constructors can be recognized before skipping a balanced body. This records bounded header/body positions while constructor body semantics and the whole Java declaration denominator remain UNKNOWN. Bounded untyped lambda initializers establish direct field names only after complete parameter, arrow, body and remaining-declarator checks (512 expression tokens, 64 parameters/statements). Typed/annotated/nested lambdas, local declarations, unsupported bodies, malformed/trailing syntax and budget excess remain UNKNOWN; quoted and empty literal tokens are checked structurally without retaining values. Parameter shadowing remains local; lambda execution, assignment/body type compatibility and values are not modeled. Each type emits one source-bound directMemberInventory; final source-scope absence checks, including scopes without a platform ancestor, must match that delivered catalog. Single and wildcard selected static-field bindings use declarationProofVersion=1 and require the exact actual field declaredType/resolved spelling plus declaring-owner id/name/kind/path/digest and declaration/header/body containment. Missing, conflicting or altered delivered dependencies withdraw API evidence; no constructor-body proof is implied.

Inline platform definitions are matched by both ID and canonical JSON content. Repeated definitions with identical content are equivalent within the existing 64-entry validation limit; object key order is ignored, while array order and JSON value types remain significant. Conflicting definitions sharing an ID never choose a winner by array order: dependent type/API proofs become `UNKNOWN` with `platform_inheritance_definition_conflict`, while independent sibling evidence is retained. The source model and six canonical platform contracts are unchanged. Validation logically coalesces equal duplicates; it does not assert that every producer emits duplicate definitions. A malformed definition or excess serialized definition slots fails closed. `platformInheritance` schema 2 uses separate direct and propagated proof definitions and validates the actual consumer location. Legacy references without an emitted origin remain `UNKNOWN`.

`platformInheritance` schema 2 links each typed consumer to a bounded `platformTypeProofs` graph. Direct proofs identify an actual emitted declaration or source syntax location, its owner, type spelling, namespace, path and source digest. Source type/method declaration and body ranges, bounded import observations and exact callsite identities support comparison. Inline proof IDs and JSON pointers are not separately queryable source records. This is static source evidence under the declared Java SE 21 assumption; the actual target JDK, runtime values, dispatch, execution and business-policy completeness remain `UNKNOWN`.

Cached validity of a `platformTypeProofs` definition never replaces validation of each actual consumer: its IR location, role, type and check references must match before a cached dependency result is reused. A valid donor proof cannot authorize a different consumer, regardless of traversal order.

## Shared raw-record transport

The downloadable raw JSON retains the original serialized bytes. Repeated keys and strings in the separate JavaScript carrier may use a deterministic dictionary and a shared, bounded decoder; the decoded values match the previous JSON.parse carrier. Pages whose packed carrier is not smaller, and pages containing valid JSON integers that round to non-finite JavaScript numbers, use the previous carrier. This preserves existing browser numeric precision and range limits; it does not turn JavaScript numbers into exact decimal arithmetic. The raw JSON remains available for consumers that need the original numeric representation. The packed decoder validates closed tags, references, duplicate keys, record count, depth and byte limits. All five language routes retain offline navigation, raw downloads and the existing 3D page scope. No fetch or HTTP server is required. Transport validation is separate from native browser, accessibility, performance and policy-meaning validation.

## Bounded generic instanceof syntax

The Java capability adapter retains the subject, qualified or nested type segments, reference-array dimensions, pattern binder, negation and branch context for supported unbounded-wildcard forms such as `Map<?,?>` and `List<?>`. Extended type nodes use `op: type_reference` and `syntaxVersion: java.instanceof.type.v1`. They remain syntax-only, `partial`, with `instanceof_runtime_unresolved`; runtime matching, compilation validity and the actual target Java version remain `UNKNOWN`. This does not infer the binder's receiver type, field values, execution or approved business meaning. Java SE 21 is the syntax reference, not evidence of the application's compiler configuration.

The expression limit remains 512 tokens and 32 parser recursion entries, not 32 edges in the final left-folded tree. Extended types allow at most 32 qualified segments, 32 total wildcard slots and 32 array dimensions; the shared type reader and conservative fallback each consume at most 512 tokens. Existing plain qualified types keep their prior expression limits. Bounds, concrete or nested type arguments, annotated and record patterns, malformed syntax and exceeded limits remain unsupported/UNKNOWN with source positions and reasons.

Possible pattern names conservatively suppress conflicting outer or platform bindings within the enclosing callable, or a local block/expression when callable ownership is unavailable. An exhausted scan or unresolved owner retains a local uncertainty reason; it does not block unrelated methods or files. Existing source identities and CALLS remain separate from this syntax capability. Raw JSON/MCP/HTML and source-bundle SQLite preserve the syntax; graph/RDF projections do not certify its full meaning. A consumer that cannot interpret the required node/version must keep UNKNOWN or reject interpretation rather than drop the type or binder. Independent policy-writer validation and native-browser behavior are separate gates. These rules use language syntax and provenance, without application-specific file, method or business-word conditions.

A nested lambda is its own callable boundary: a pattern inside it cannot suppress an independent outer invocation. API operands use their actual lexical occurrence; flattened name-only reference summaries may remain UNKNOWN when occurrences belong to different scopes.
